# Architecture

A Turborepo + Bun monorepo. A TanStack Start app, built as a Bun server on Railway, serves the app UI with SSR; a second TanStack Start app is prerendered into the static landing that Caddy serves; the API on Railway serves Better Auth at `/api/auth`, the oRPC API at `/api/rpc`, the calendar feed and the PostHog proxy, and is the only code that reaches the database. The browser calls the API host directly with credentials; the session cookie covers the app and the API through the environment's shared domain. Terms: [UBIQUITOUS_LANGUAGE.md](UBIQUITOUS_LANGUAGE.md). Decisions: [docs/decisions](docs/decisions).


Dependencies point one way. Packages are plain TypeScript and React without Effect; the API owns the Effect services and layers. Code moves into a package only when a second consumer needs it ([ADR 0002](docs/decisions/0002-package-layout.md)). The Expo app, `apps/mobile`, may use only the DOM-free hooks and helpers of `packages/app` with `packages/contracts` and `packages/domain`, and never `packages/ui` ([ADR 0017](docs/decisions/0017-expo-mobile-app.md)).

## Request flow

```
browser (orpcQuery + TanStack Query, VITE_API_URL) ─┐
SSR (rpc.client.server, API_INTERNAL_URL) ──────────┤
  → API: withCors → withClientIp → createRpcHandler (Origin check, context, RPCHandler)
    → router procedure (Effect) → service → port → adapter
```

One `RPCLink` serves the browser and SSR; `orpcQuery` from `@soonlane/app` calls through it. The browser calls the API's public origin, `VITE_API_URL` (build time), with `credentials: 'include'`, and so does the Better Auth client. SSR calls the API directly at the runtime variable `API_INTERNAL_URL` and sends only this environment's Better Auth `session_token`, `session_data` and `dont_remember` cookies (`<prefix>.<name>`, `__Secure-<prefix>.<name>` on https, prefix from `VITE_AUTH_COOKIE_PREFIX`) and `<prefix>.consent`, by exact name, the visitor's IP in `x-soonlane-visitor-ip` (Railway's `X-Real-IP`, or `CF-Connecting-IP` when that address is a Cloudflare edge, through `resolveEdgeIp` from `@soonlane/auth/client-ip`, the same rule the API applies; the socket address locally) and `API_PROXY_SECRET` in `x-soonlane-proxy-secret`. Every `Set-Cookie` of the answer goes onto the page's response, so a session refreshed by `identity.me` sticks.

The API's entry answers CORS for `/api/auth` and `/api/rpc` (`withCors`). A preflight from an origin in `TRUSTED_ORIGINS` gets 204 with that exact origin, credentials, `GET, POST`, `content-type` (all the oRPC link and the Better Auth client send) and a two-hour cache. The desktop app's bundled page (`DESKTOP_PAGE_ORIGIN`, `views://app`) gets its exact origin without credentials and may also send `authorization`, for its bearer token, and its responses lose any `Set-Cookie`; it is not in `TRUSTED_ORIGINS` (where `views://app` would parse to the origin `null` anyway), so it is never a return address and never receives the cookie. Any other origin gets 403, including other `soonlane.com` hosts and the API's own. Other requests with an allowed `Origin` carry the same headers, on errors too; any other `Origin` gets 403; a request without `Origin` (SSR, Google's redirect back, the desktop app's main process) passes to Better Auth and oRPC, whose own origin checks stay on. The RPC handler repeats the origin check before it looks up the session and refuses a request from the desktop page that carries a cookie.

`createRpcHandler` also rejects any `Origin` outside `TRUSTED_ORIGINS`, except the desktop page's when it carries no cookie. Only `POST` reaches procedures. A session lookup that refreshes or deletes the session cookie returns its `Set-Cookie` values (`getSession` with `returnHeaders`), and the handler appends each to that request's response. `system.health` returns `{ ok, db, version, commit }`. `system.desktopSupport` takes a desktop app's version and answers whether this API still serves it, against `DESKTOP_MINIMUM_VERSION` (unset, every version is), with `Bun.semver`, so a prerelease of the minimum counts as older; `system.mobileSupport` does the same for the iPhone and Android app against `MOBILE_MINIMUM_VERSION`.

## Client IP

The API's HTTP entry (`withClientIp`) settles one address per `/api/auth` and `/api/rpc` request and writes it into `x-soonlane-client-ip`, the only header Better Auth reads; an incoming copy is dropped. With `x-soonlane-proxy-secret` the request comes from the web server: the secret is compared in constant time (both sides hashed), a wrong one gets 403 and a log line without the value, and the right one makes the API take `x-soonlane-visitor-ip` if it is one valid address, else 400. Without the secret header the API takes Railway's `X-Real-IP` (missing or invalid: 400); when that address is in Cloudflare's published ranges (the proxied production host), it takes `CF-Connecting-IP` instead (one valid address, else 400). A client that reaches Railway directly shows its own address in `X-Real-IP`, so a forged `CF-Connecting-IP` is ignored. With `APP_ENV=development`, where no edge sets an address, a request that would get 400 for a missing one counts as `127.0.0.1` instead. The secret and visitor headers never reach a handler or a log. `/health` and the calendar feed skip this step.

## Tasks

A task belongs to the user who created it, its owner (`task.owner_id`, cascade on user delete) and has a title, an optional description, an optional due date (`date`, no time zone; a task without one has no due time and no repeat rule, which the contract checks), an optional due time (`time`), a priority 1 to 4 (default 4), `created_at` and a nullable `completed_at`. `tasks.list` serves every view of open tasks. It takes the browser's `today` and optional filters: `from` and `to` together limit the scheduled tasks to a range (without them every task due from `today` on is scheduled), `labelId` keeps the tasks with that label and `projectId` the tasks in that project; every filter given applies. It returns the open tasks without a due date (undated; without a label or project filter only those without a project, the Inbox), those due before `today` (overdue) and the scheduled ones, read in one query in the order `TASK_DAY_ORDER` in `@soonlane/domain` defines (date with undated last, time with untimed last, priority, then age). Completing is optimistic in the TanStack Query cache and offers Undo (`tasks.uncomplete`). A task can carry a repeat rule (`repeat_unit`, `repeat_interval`, `repeat_anchor`, all set or all null, enforced by checks); completing a repeating task takes the browser's `today` and moves its due date to the next occurrence (`repeat-rule.helper`) instead of setting `completed_at`, with an update conditional on the due date the client showed (the stored one for older clients), and Undo sends the previous due date back. `tasks.edit` writes only the fields it carries, so a tab with an older copy of the task does not write it back over changes made elsewhere: absent keeps a field, `null` clears the description, due date, due time, repeat rule, goal or project, and no due date also clears the time and the rule; two edits of the same field are last write wins. An edit that carries neither a due date nor a rule leaves the schedule columns alone; one that carries a due date snaps it and moves the anchor to it only when it changes the date or the rule. A version check was rejected: it needs a migration and a bump on every write path, and a menu change should apply, not be refused. `tasks.update` stays for desktop apps that bundle a UI from before `tasks.edit` until the API can ask them to update (SOON-152): it replaces the title, description, due date and time and priority (an absent description, date or time becomes `null`), keeps an absent repeat rule, goal or project, and runs as the same edit. Optional `labelIds` replace the task's labels in the same transaction as the row, absent keeps them. The cache moves the edited task at once to the day, Overdue or range its new date belongs to, shows its new labels, and takes it out of a label view whose label it lost; a failed save puts it back everywhere. Reschedule on Overdue moves the shown overdue tasks to one day (`tasks.reschedule` takes their ids, skips completed and foreign ones and keeps due times), also optimistically; it changes only the due date, so a repeating task keeps its rule and anchor. `tasks.delete` removes a task for good in one `DELETE` filtered by owner (another user's task is NOT_FOUND), its `task_label` rows go by cascade, and the cache drops it at once, putting it back if the request fails. `tasks.listCompleted` takes `{ from, to }`, the browser's local midnights around its today, and returns the tasks completed in that half-open range, last completed first, with `earlierCompletedAt`, the latest completion before `from`; Today shows them under Completed. The Completed view (`/completed`) pages back through windows of 14 local days with `useInfiniteQuery`: each next window ends with the local day of `earlierCompletedAt`, so empty stretches are skipped, and the browser groups the tasks by the local day of `completedAt`. `tasks.search` takes `{ query }` (trimmed, 1 to 100 characters) and returns the owner's tasks whose title or description contains every word of it, case-insensitive and with `%`, `_` and `\` matched as typed: open tasks in day order, then completed ones, last completed first, at most 50 with `hasMore` for the rest. Search (`/search`) keeps the query in React state only and sends it 300 ms after the last keystroke; every task change refetches its results too. The search palette (⌘K) runs the same search and hands its query to the page in navigation state, never in the URL; `tasks.get` loads one of the owner's tasks for its Recent list. Every task the API returns carries its labels and its project, each loaded in one query per list query; advancing a repeating task updates the same row, so it keeps its labels. A subtask is a task row with `parent_id` and a stored `depth`, 4 levels at most and 50 per parent, linked by a composite key on `(owner_id, parent_id)` that cascades deletes; every task also carries its parent's title and its subtasks' done and total counts. Open lists leave out undated subtasks, `tasks.listSubtasks` returns one parent's subtasks, and completing, reopening or advancing a task carries over to its subtasks under a lock on the task's ancestors ([ADR 0018](docs/decisions/0018-subtasks-as-task-rows.md)).

## Labels

A label belongs to the owner (`label.owner_id`, cascade on user delete) and has a name and an optional color, one of Todoist's 20 palette colors as a kebab-case key (`LABEL_COLORS`, e.g. `sky-blue`; no color means the default color in the UI). Names are trimmed, 1 to 60 characters and unique per owner ignoring case, enforced by a unique index on `(owner_id, lower(name))`: `labels.create` and `labels.update` write without checking first and the service maps the index violation to CONFLICT, so concurrent creates and renames to a taken name also return CONFLICT. `task_label` joins tasks and labels (cascade on both), so deleting a label takes it off every task. `tasks.create`, `tasks.edit` and `tasks.update` take optional `labelIds` (no duplicates) and write the task and its labels in one transaction, leaving out ids that are not the owner's labels; on an edit they replace the task's labels, and an empty list takes them all off. `tasks.assignLabel` and `tasks.unassignLabel` are idempotent and write only when the task and the label both belong to the owner; another user's task or label is NOT_FOUND. Labels are sorted by lower-cased name, then age. `labels.list` also counts each label's open tasks (`openTaskCount`) in the same query; creating, editing, completing and uncompleting a task, and renaming or deleting a label, refresh it along with the task lists. The sidebar lists the labels, links each to `/labels/$name` and adds, renames and deletes them.

The label view at `/labels/$name` finds the label by name ignoring case in `labels.list` (its loader fills the tab title) and shows a not-found page for any other name. It calls `tasks.list` with `{ labelId, today }`, which returns the label's open tasks, undated, overdue before `today` and scheduled from it; a label that is not the owner's is NOT_FOUND. The Inbox view (`/inbox`) asks with Today's input (`getTodayListInput`) and shows only `undated`, so it shares Today's cache entry. Every view caches its list under the one `tasks.list` key, so completing, editing, logging progress and rescheduling update every task list at once, and the refreshes after a change reach them all.

## Projects

A project belongs to the owner (`project.owner_id`, cascade on user delete) and has a name: trimmed, 1 to 120 characters and unique per owner ignoring case, enforced by a unique index on `(owner_id, lower(name))`, which `projects.create` and `projects.update` map to CONFLICT like labels. A task has at most one project (`task.project_id`, nullable); deleting a project sets it to null on its tasks (`ON DELETE SET NULL`), so the tasks stay. `tasks.create`, `tasks.edit` and `tasks.update` take an optional `projectId`; one that is missing or not the owner's is NOT_FOUND and nothing is written, and so is a project deleted between that check and the write (the foreign key violation maps to the same error). On `tasks.update` an absent `projectId` keeps the project and `null` clears it, like the repeat rule and the goal, so edits that do not show the project never drop it. `projects.list` is sorted like labels and counts each project's open tasks (`openTaskCount`). `tasks.list` with `{ projectId, today }` returns the project's open tasks; a project that is not the owner's is NOT_FOUND. The sidebar lists the projects above the labels and adds, renames and deletes them; the project view at `/projects/$name` works like the label view, and its Add task row puts each new task in the project. Creating, editing, completing and deleting a task and renaming or deleting a project refresh `projects.list` along with the task lists, and the cache places an edited task in a project view only when it has that project.

## Landing

The app and the landing are two apps on two hosts ([ADR 0013](docs/decisions/0013-three-hosts-on-railway.md), update of 2026-11-13 for SOON-128). In `apps/web`, the pathless `session` layout wraps the app at root paths on any host (the `shell` layout with Upcoming at `/`, `/inbox`, `/today`, `/search`, `/completed`, `/labels/$name`, `/projects/$name`, `/todoist`; `/quick-add`, `/login` and the desktop sign-in routes): its `beforeLoad` calls `identity.me` and its `head` adds `noindex, nofollow`. `public/robots.txt` blocks every crawler, and the app links to the legal pages and the changelog by absolute URL on `VITE_LANDING_URL`. `apps/landing` serves `/`, `/privacy`, `/terms`, `/changelog`, `/blog` and `/blog/$slug` on `soonlane.com`; its root route is the document and the layout with header and footer, and it never reads the session, so its pages make no request to the API besides PostHog's `/ingest`. Links to the app are plain anchors on the app's origin. The header and the home page's call to action show "Open app" instead of "Log in" and "Get started" when the browser holds the `<prefix>.signed_in` hint cookie (`soonlane.signed_in` in production): a head script marks `<html data-signed-in>` before first paint and the `signed-in:` Tailwind variant picks between the two variants in the prerendered HTML.

TanStack Start prerenders the whole landing during `vite build` (`prerender` and `pages` in `apps/landing/vite.config.ts`): the crawl follows links from the listed pages, and the server routes for `/robots.txt`, `/sitemap.xml` and `/blog/rss.xml` and the `/404` route are prerendered into files too (`404.html`). Caddy serves `dist/client` alone (`apps/landing/Caddyfile`): `immutable` for `/assets/*`, `no-cache` for everything else, `404.html` with status 404 and `no-store` for an unknown path, the feeds' content types, the security headers and `/health`. The build reads only `APP_ENV` and `VITE_POSTHOG_KEY`; `APP_ENV` picks the app's and the API's origins and the cookie prefix from `LANDING_ENVIRONMENTS` (`landing-environment.constants.ts`). `/changelog` loads the releases parsed from `CHANGELOG.md` (`virtual:changelog`, read in `vite.config.ts`) with a dynamic import, so the text stays out of the main bundle. `bun run build` ends with `scripts/check-static.ts`: a page for every sitemap URL, robots for this `APP_ENV` and the not-found page. Legal pages are MDX in `modules/landing/content` with `title`, `description` and `updated` frontmatter, compiled by content-collections into `.content-collections/generated` (imported as `content-collections`; `bun install` and `typecheck` generate it). Blog posts are MDX in `modules/blog/content`; a production build (`APP_ENV=production`) skips drafts and future-dated posts in the collection transform, so their text never reaches the output, and other builds mark them with a `published` flag that shows the Draft label and `noindex`. The post data is a chunk of its own that only the blog routes load. The sitemap lists published posts only. Before `vite build`, `apps/landing/scripts/og-images.tsx` draws a 1200×630 share image for every post in the generated data (satori and resvg, devDependencies only) into `public/og/blog/<slug>.png`, which is gitignored; a post's own `image` frontmatter replaces it.

`apps/web` keeps its hosting in `modules/hosting` as Start request middlewares, registered in `src/start.ts` after Start's CSRF check for server functions, which Start drops once a start instance exists and which also accepts the host's `https://` origin because Railway's edge ends TLS: `compression.middleware.ts` gzips text responses outside development (Nitro's own static files are precompressed at build time), and `error-cache.middleware.ts` gives every 4xx and 5xx, a missing asset's 404 included, `no-store`. The Nitro config adds `public, max-age=31536000, immutable` to files under `/assets/` that exist, `no-store` to the sign-in hand-off pages under `/desktop/` and `/android/`, and `no-cache` to every other success; those rules match only that letter case, so `identity`'s `hand-off-path.middleware.ts` answers 404 to any other, such as `/Android/callback`, which the router would render. `/.well-known/assetlinks.json` (`routes/asset-links.route.ts`) lists the Android app with the certificate hashes in `ANDROID_CERT_FINGERPRINTS`, read per request, or nothing without them; only the app host serves it and the Android hand-off pages, because the site's Caddy has no such files and answers 404. `/health` (`routes/health.route.ts`) answers `{ ok, environment, commit }` without the API, for Railway's health check. `bun run build` ends with `scripts/check-server.ts`, which starts the built server from a copy outside the repo and checks robots, the app at `/`, `/today` and `/login`, a 404 for `/privacy`, compression, both asset cases, `/health`, the asset links, the Android callback page's `no-store` and `no-referrer`, and a 404 with `no-store` for `/Android/callback`.

Canonical links, Open Graph URLs and the sitemap use the constant `LANDING_URL` (`https://soonlane.com`) in every environment. `robots.txt` is written at build time: a production build allows `/`, disallows `/api/` and `/calendar/` and points to the sitemap; every other build disallows everything, and the app's host always does. A new public page needs a link from a crawled page or an entry in `pages`, and an entry in `SITEMAP_ENTRIES`; blog posts need neither.

A task can carry a goal: `goal_target` (1 to 10,000), an optional `goal_unit` (up to 24 characters) and `goal_progress`, the progress of the current occurrence (0 to the target; check constraints keep the three consistent). `tasks.logProgress` takes the amount with the browser's `today` and the due date it showed, and applies it in one `UPDATE` computed in SQL on the row it locks, so concurrent logs never lose an increment: progress is clamped to 0 and the target. On a task that does not repeat, reaching the target sets `completed_at`, and a log that takes it back below the target clears it again, which is how Undo works there. On a repeating task, reaching the target moves the due date to the next occurrence and resets the progress to 0 in the same statement, only while the task still has the due date the client showed; otherwise the log counts toward the current occurrence and nothing advances. Completing a repeating goal task with the circle resets its progress the same way; on a task that does not repeat the circle never touches progress. The response carries `logged`, the amount the server applied after clamping, and `completed` when this log completed the task: the due date it was completed on and the progress before the log. `completed` decides the "Task completed" toast and the `task_completed` event. Undo of a repeating task, from a log or the circle, calls `tasks.uncomplete` with the previous due date and progress (clamped to the target, ignored without a goal); the circle takes that progress from the cached row. Undo of a task that does not repeat logs `-logged`. Logging is optimistic in every task list. A log's own refresh waits until no other log is pending; refreshes from other mutations are not held back. `tasks.edit` and `tasks.update` take an optional `goal`: absent keeps the goal and its progress, `null` clears target, unit and progress, and a new target clamps the progress to it, all on the row it locks first, so the progress check never fails. An edit that leaves an open task's progress at its target (a lower new target, or the kept one of a task reopened at its target) completes it like a log, so no open task sits at its target after an edit: a task that does not repeat gets `completed_at`, a repeating one moves to its next occurrence from the edited due date (with the browser's `today`) and starts at 0. The response's `completed` then carries the due date it completed on, the previous progress and the previous goal, and Undo sends all three back to `tasks.uncomplete`, which restores the goal before clamping the progress to it.

## Calendar subscription

Each account can have one private calendar link ([ADR 0011](docs/decisions/0011-private-calendar-subscription-link.md)). `calendar.createSubscription` draws a 256-bit token, stores only its SHA-256 in `calendar_subscription` (keyed by `owner_id`, cascade on user delete) and returns `<API_URL>/calendar/<token>.ics` (`https://api.soonlane.com/...`) once; creating again replaces the row, so the old link stops working. `calendar.getSubscription` returns only the creation time, and `calendar.revokeSubscription` deletes the row. The API's `GET /calendar/<token>.ics` needs no session: a malformed, unknown or revoked token gets an empty 404, a known one the owner's open tasks with a due date from `TasksService.listOpen` as `text/calendar`, with `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow` and `Referrer-Policy: no-referrer`. Each task is one event on its due date: all day without a due time, a floating local time with a 30-minute duration and an alarm at its start with one; the summary is the title, the description the task's description and labels, the URL `APP_URL` + `/` on the app host, the UID `<taskId>@soonlane.com`. The feed asks for a refresh every 15 minutes. Any other method on that path, and any other path under `/calendar/`, gets the same empty 404 with the same headers, and the web app has no `/calendar` routes. The handler catches every failure, logs only the error name and never the URL or the token.

## Sign-in

Better Auth with Google and email codes at `/api/auth`, configured by `createAuth` in `packages/auth` and built once by `BetterAuthLive` from `AppConfig` and `Db` ([ADR 0003](docs/decisions/0003-better-auth-in-a-package-behind-an-effect-layer.md)). Any Google account with a verified address can sign up and gets its own tasks; a non-empty `ALLOWED_EMAILS` limits new accounts to those addresses and leaves existing ones alone ([ADR 0009](docs/decisions/0009-open-sign-in.md)). "Delete account" in the user menu calls Better Auth's `/delete-user`, which removes the user with its sessions, accounts and tasks. A before hook (`packages/auth/src/account-deletion.handler.ts`) first requires the session to have started with a Google login at most 5 minutes old. It reads `auth_time` from the ID tokens stored on the user's Google account rows and otherwise answers `SESSION_EXPIRED`, which the clients turn into a fresh sign-in. When the login is old but the session started after it, Google let that sign-in through without checking the user, and the answer adds `reason: GOOGLE_LOGIN_NOT_RENEWED`: the web dialog and the Android app ask the user to sign out of Google in the browser first. Every Google sign-in asks Google for `auth_time` through the `claims` parameter, and Google returns it only while "Session age claims" is on ([ADR 0009](docs/decisions/0009-open-sign-in.md), SOON-51 update). Better Auth runs on the API and rate limits `/api/auth` per client IP (see Client IP) in the `rate_limit` table: 100 requests a minute, 10 for Google sign-in, linking Todoist or Linear, each desktop sign-in step and the mobile app's `/expo-authorization-proxy`, 5 deletions an hour. Its base URL is the API's origin (`API_URL`), so Google returns to `https://api.soonlane.com/api/auth/callback/google` (staging `https://api.staging.soonlane.com/...`). Cookies carry the environment's prefix (`AUTH_COOKIE_PREFIX`: `soonlane`, `soonlane-staging`) and its domain (`AUTH_COOKIE_DOMAIN`: `soonlane.com`, `staging.soonlane.com`), so the session (`__Secure-soonlane.session_token`) reaches the web app and the API ([ADR 0013](docs/decisions/0013-three-hosts-on-railway.md)). Every new or refreshed session also sets `<prefix>.signed_in=1` with the session cookie's attributes but not HttpOnly (no user data), so static pages can show "Open app"; sign-out and deletion clear it. The `returnAddresses` plugin (`packages/auth/src/return-address.handler.ts`) runs before Better Auth routes a request and accepts return addresses (`callbackURL`, `errorCallbackURL`, `newUserCallbackURL`, `redirectTo` in the body, every `callbackURL` in the query) only as absolute URLs on a `TRUSTED_ORIGINS` origin or, on `/sign-in/social` only, with the mobile app's scheme (`soonlane:`, and Expo Go's `exp:` when `APP_ENV` is `development`), and `/sign-in/social` must carry a `callbackURL` in its body; anything else gets 400. Better Auth's errors redirect to the web `/login?error=…` (`onAPIError.errorURL`). Google only signs in; Todoist and Linear, when configured, are only linked to a signed-in account (`/sign-in/social` refuses them, `/link-social` accepts nothing else, takes no scopes or extra parameters and refuses while the user has a row of that provider). Provider tokens are stored encrypted with `AUTH_SECRET`, and the endpoints that return them to the browser (`/get-access-token`, `/refresh-token`, `/account-info`) are disabled, as is `/unlink-account`. Production's `.soonlane.com` cookies also reach staging hosts, so the staging API receives production session tokens on every browser call. Staging never reads them (own `AUTH_SECRET`, own prefix, SSR forwards only its own prefix's cookies, and the API never logs the cookie header), so staging runs only trusted refs ([ADR 0013](docs/decisions/0013-three-hosts-on-railway.md)). Details: [docs/deploy-railway.md](docs/deploy-railway.md).

Email codes come from Better Auth's `emailOTP` behind `emailCodeSignIn` (`packages/auth/src/email-code.handler.ts`, [ADR 0009](docs/decisions/0009-open-sign-in.md), SOON-201 update): `/email-otp/send-verification-otp` mails a six-digit code through the API's `Email` port and always answers success, and `/sign-in/email-otp` trades the address and code for a session cookie, creating the account on the first sign-in. Codes last 10 minutes and allow 3 attempts; a resend within that time mails the same code. Sending is limited to 3 a minute per IP and 5 an hour per address (`rate_limit`, keyed by an HMAC of the address), signing in to 10 a minute per IP. Either method may be off: Google needs `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, email needs `EMAIL_FROM` with `RESEND_API_KEY` or `SMTP_URL` (development falls back to the log), and the API refuses to start with neither; `identity.signInMethods` tells the sign-in screens which are on. A Google sign-in links onto an existing account only when Google vouches for the address (Gmail or a Workspace `hd`). Account deletion also passes for a session an email code started at most 5 minutes ago (`session.email_code_at`, which the desktop and Android hand-offs copy from the browser session), and its `SESSION_EXPIRED` refusal lists the methods in `reauth`.

The desktop app signs in through the system browser ([ADR 0007](docs/decisions/0007-desktop-sign-in-through-the-system-browser.md), [ADR 0015](docs/decisions/0015-desktop-app-with-its-own-ui.md)). The `desktopSignIn` plugin in `packages/auth` lets the signed-in browser trade the app's PKCE challenge for a one-time code (2 minutes, stored hashed in `verification`) at `/desktop/sign-in?challenge=…&port=…`, after a click on "Open the desktop app" that sends the browser to the app's loopback listener, `http://127.0.0.1:<port>/callback?code=…` (RFC 8252). The main process trades the code and the verifier at `/desktop-sign-in/token` for a desktop token: the session token signed with `AUTH_SECRET` like the cookie, returned in the body with `no-store`. The app sends it as `Authorization: Bearer`; Better Auth's `bearer` plugin, with `requireSignature` and without its after hook (which would expose the web session's cookie value in a `set-auth-token` header), turns it into the session cookie for that request, so `getSession` is unchanged. Better Auth's `/sign-out` with the bearer token revokes the desktop session. The app gets a session of its own, so signing out in the app leaves the browser signed in. The desktop session keeps the browser session's `createdAt` and `emailCodeAt`, so account deletion's checks apply to it unchanged; the check on `/delete-user` runs the registered `bearer` hooks itself to read the session the endpoint acts on, because no before hook sees what another returns ([ADR 0009](docs/decisions/0009-open-sign-in.md), SOON-226 update).

The iPhone app signs in through Better Auth's Expo plugin (`@better-auth/expo`, [ADR 0017](docs/decisions/0017-expo-mobile-app.md)). `createAuth` adds `soonlane://` (and `exp://` in development) to Better Auth's trusted origins, never to `TRUSTED_ORIGINS`, and leaves out the plugin's `init`, which would trust `exp://` whenever the bundle's `NODE_ENV` is `development`. The app opens `/expo-authorization-proxy` in the iOS sign-in sheet; the proxy sets the OAuth state cookie in that browser and goes on to Google, and after the callback the plugin copies the response's `Set-Cookie` into the `soonlane://` redirect as `?cookie=`, and `expoSignIn` then drops it from the response, so the browser that finished the callback gets no session. Because the proxy signs the state into whichever browser opens it, a before hook lets it through only for a Google authorization URL whose state is a pending sign-in without a link that returns only to the app's scheme; otherwise a Todoist link someone else started would link the opener's Todoist account to the starter's. The app sends the cookie as a `Cookie` header without `Origin`, so `withCors` and the RPC handler pass it as before; on `/api/auth` the plugin turns the app's `expo-origin` header into `Origin` for Better Auth's own origin check, only when a request has no `Origin`. An app session is an ordinary Google session, so deletion's Google-login check applies to it unchanged. In the app (`apps/mobile/src/platform/auth/auth.client.ts`), `expoClient` keeps the cookie in the Keychain (`expo-secure-store`) under the environment's prefix (`EXPO_PUBLIC_AUTH_COOKIE_PREFIX`, set per EAS profile), and `signInWithGoogle` opens the sheet itself (`disableRedirect`, since the plugin drops the return's `error`) with `preferEphemeralSession`, so it shares no cookies with Safari, and takes a session and an error only from that sheet's result, storing the cookie through the plugin's storage; `app/+native-intent.tsx` keeps only the route of every other link that opens the app, and sends a link that carries `cookie` to the start screen. The oRPC link sends the client's cookie header with `credentials: 'omit'` and `x-soonlane-app: mobile`, on which the API's session lookup never refreshes the session, because the Keychain takes refreshed cookies only from the auth client's own `/get-session`. The root layout shows only the sign-in screen until Better Auth's `useSession` has a session, and clears the TanStack Query cache whenever the signed-in user changes or the session ends. It also asks `system.mobileSupport` with the app's version, again on each return to the foreground, without waiting for the answer; an app the API no longer serves shows only an update screen, signed in or not, which on iPhone opens TestFlight. Sign-out always ends the session on the phone and, when the request gets through, on the server; a reply it overtook is dropped and no sign-in starts until it settles.

The Android app signs in through the desktop app's hand-off instead, because Android has no system auth session and any app can claim `soonlane:` ([ADR 0017](docs/decisions/0017-expo-mobile-app.md), SOON-177 update). `src/platform/auth/android-hand-off.client.ts` makes a verifier with `expo-crypto`, opens `/android/sign-in?challenge=…` on `EXPO_PUBLIC_WEB_URL` in a Custom Tab and listens, only while that one attempt is pending (from the tap until a code, Cancel, a session end, a newer attempt or ten minutes), for the App Link `https://<app host>/android/callback?code=…`; `signInWithGoogle` in `auth.client.ts` then trades the code and the verifier for a session cookie at `/android-sign-in/exchange`, which shares its checks and rate limit with the desktop app's `/desktop-sign-in/token` and labels the session `mobile`, unless a sign-out or deletion started since the tab opened. The web page names the signed-in account, offers another one through `fresh=true`, and opens the callback only after a click; Android hands that link only to the app the host's `/.well-known/assetlinks.json` verifies. Each build declares one `autoVerify` host, from `app.config.ts`. When Android keeps the link in the browser, `/android/callback` is an inert page that removes its query, starts no analytics and offers an `intent:` link for the package `com.mnigos.soonlane`.

Both phones also sign in with an email code entered in the app, through the Expo client's own requests, without the hand-off ([ADR 0017](docs/decisions/0017-expo-mobile-app.md), SOON-201 update); `identity.signInMethods` decides which buttons the sign-in screen shows.

## Todoist import

With `TODOIST_CLIENT_ID` and `TODOIST_CLIENT_SECRET` set, a signed-in user can link Todoist read-only, see what an import would bring in and import it ([ADR 0016](docs/decisions/0016-todoist-link-through-better-auth.md)). "Continue to Todoist" on `/todoist` calls `todoist.cancel` (any earlier connection goes first) and then Better Auth's `/link-social`, which sends the browser to Todoist's consent screen; Todoist returns to `<API_URL>/api/auth/callback/todoist`, which writes the `todoist` row of `account` with the tokens encrypted and redirects to `/todoist` (with `?error=` when nothing was linked). The page asks `todoist.status`, and with a connection `todoist.preview`, which decrypts the access token, runs one full sync (`/api/v1/sync`, `sync_token=*`; a 429 waits for `Retry-After`, at least a second, at most 3 times and 10 seconds; the whole read stops after 20 seconds), maps it with `planTodoistImport` against the owner's label and project names and returns counts: tasks, new and matched labels, new and matched projects, and each change (`TODOIST_IMPORT_CHANGES`). Every open task counts, with or without a due date, except those already in the owner's `imported_todoist_task` records (`alreadyImported`); priority is inverted (Todoist 4 is Soonlane 1); a repeating task keeps its rule when its English due string is one rule a task name can type ("every day", "every 2 weeks", "every! 3 days", "every fri", "every 15th", "every jan 27"), optionally followed by "at" and a time, and the rule is stored as a new task's with its due date as the anchor; any other repeating task ("every mon, fri", "every 3rd friday", "starting", another language) arrives once on its current date and counts under `repeating`; projects and sections count when they hold an imported task, and the Inbox is not a project; a project matches an existing one by name ignoring case, and nested projects arrive flat. "Import into Soonlane" calls `todoist.import` with the browser's time zone; it reads Todoist again with the same guards, plans the same way and saves in one transaction: the records of the planned tasks first (`onConflictDoNothing` on owner and Todoist id, so a second submit or tab waits on the keys and saves nothing), then the missing projects and labels (`onConflictDoNothing` on their name indexes, a label taking its Todoist color when it is in `LABEL_COLORS`), then the tasks and their labels, 1,000 rows per insert. A date-only or floating due stays as written; a due pinned to UTC moves into the browser's time zone; a task without a due date arrives without one, so an Inbox task without a date lands in the Inbox. The records outlive their tasks, so a deleted or completed task does not come back. The import closes the connection on success and on failure, and sends `todoist_imported` after the commit. A failed preview, a cancel, a new link and a sweep every minute for rows older than 15 minutes revoke both tokens at Todoist and delete the row; a row whose revocation fails stays for the next sweep, and goes after an hour regardless, and meanwhile `todoist.cancel` fails so no new link starts. Tokens from a callback that stored no row are revoked by the callback's after hook. Todoist failures are logged by HTTP status or error name only, never with the token, URL or response body. The desktop app opens `/todoist` in the system browser.

## MCP

AI agents connect through OAuth with Better Auth's MCP plugin ([ADR 0020](docs/decisions/0020-mcp-clients-connect-through-oauth.md)). `mcpAuthorization()` in `packages/auth` adds the `jwt`, `mcp` and `cimd` plugins to `createAuth`: the issuer is the API's origin, tokens are JWTs for `<API_URL>/mcp` with `tasks:read`, `tasks:write` and `offline_access`, and clients identify themselves with a Client ID Metadata Document, fetched over a pinned connection. The API routes `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource[/mcp]` to Better Auth. Open dynamic registration is the `dynamicMcpRegistration` option, off. An agent's authorization sends the browser to `/login` when signed out and then to the web app's `/mcp/allow`, which names the agent and where the answer goes and lets the user untick what the agent asked for (the `access` search param). "Connected agents" in the user menu (`@soonlane/app`'s `McpConnectionsDialog`, on the web and in the Mac app) lists connections through `mcp.listConnections`; `mcp.disconnect` deletes the connection with its tokens, and an hourly sweep removes connections unused for 30 days. The empty list shows the server address, `<API_URL>/mcp`, which `mcp.listConnections` returns, with a Copy button.

`/mcp` serves MCP over streamable HTTP, stateless, with `@modelcontextprotocol/server`'s `createMcpHandler` (`legacy: 'stateless'`, so 2025 clients keep working) and a new `McpServer` per request. A request with an `Origin` header gets 403. The `Auth` port's `serveMcpRequest` verifies the token through the plugin's `requireMcpAuth`; then `McpService.admit` requires the user's connection to the token's client, allowed no later than the token's `iat`, counts the request in `rate_limit` (120 a minute for all of a user's agents, then 429) and records "last used" at most once a minute. A token without a connection gets the same 401 challenge as an invalid one. Allowing an agent the user has no connection to first deletes everything still issued to it for that user (`clearEarlierMcpGrants` in `packages/auth`), so codes and refresh tokens from before a Disconnect cannot mint tokens under the new connection, except a token request already in flight during that Allow; an access token issued in the same whole second as the Disconnect and the completed new Allow still passes ([ADR 0020](docs/decisions/0020-mcp-clients-connect-through-oauth.md)). The scopes are the token's and the connection's together; `tasks:read`, which `tasks:write` implies, registers seven read tools (tasks for a view, search, one task, subtasks, completed tasks, projects, labels), and `tasks:write` eight write tools (add, edit, complete, reopen and reschedule tasks, add and take off a label, log goal progress) that never delete; all call the services with the token's user and parse their arguments with the contract's schemas (`mcp-tool.schemas.ts`). On a read-only connection a write tool called by name answers that the agent can only see tasks. Each request logs one line: status, tool, outcome, error code and duration; the server declares `tools.listChanged: false`.

## Database

Railway Postgres 18 through `pg` and Drizzle ([docs/railway-postgres.md](docs/railway-postgres.md)); locally Postgres 18 from `compose.yaml`. `Db` owns one pool per runtime (10 connections for the one long-lived process, 10 s `query_timeout`, an `error` listener) and closes it when the runtime is disposed; `Db.run` is the only place that creates `DbError`. `Db.transaction` runs a transaction through it and runs it again, up to 3 more times, when Postgres aborts it as a deadlock (`40P01`) or serialization failure (`40001`); the task tree writes and the project delete use it ([ADR 0018](docs/decisions/0018-subtasks-as-task-rows.md)). Logs carry error names only, because driver errors embed SQL parameters such as session tokens. The API's `Bun.serve` answers any uncaught error with an empty 500 and logs only its name, for the same reason. The API's Railway pre-deploy runs the migrator before each deployment goes live; the web build never migrates ([docs/deploy-railway.md](docs/deploy-railway.md#migrations)).

## Server boundary

The web app depends on none of `@soonlane/db`, `@soonlane/auth/server`, `pg`, `drizzle-orm`, `posthog-node` or Effect; those live in `apps/api`. Its server-only code (`platform/`, `infrastructure/`, server-suffixed files, `*.handler.ts` and `routes/api.*`) never reaches the client bundle: TanStack Start import protection in `apps/web/vite.config.ts` fails the build on a leak and excludes the three browser-safe oRPC client files in `platform/rpc`. Server route handlers (`/health`) run only from `server.handlers`, which TanStack Start keeps out of the client bundle.

## Analytics

PostHog (EU) receives product events, session replays and exceptions; the tracking plan is [docs/analytics.md](docs/analytics.md). In the browser everything hangs on `VITE_POSTHOG_KEY`: without it posthog-js is never downloaded, no consent banner appears and nothing is sent. On the API, `POSTHOG_KEY` turns on server events; without it `Analytics` is a no-op. With a key, each visitor's answer in the `<prefix>.consent` cookie (`soonlane.consent`, shared by every host under `soonlane.com`; staging's `soonlane-staging.consent` under `staging.soonlane.com`) decides: nothing before an answer, full analytics and masked replay when granted, cookieless anonymous events when denied or under Global Privacy Control; once granted, posthog-js keeps its identity in a cookie on the shared domain too, so the landing and the app count one visitor; posthog-js never runs on `/desktop/*`. The browser side (consent banner, posthog-js client, browser event types) lives in `packages/analytics`; the API reads the answer through its root export. Both browser apps send through the first-party `/ingest` proxy on the API host, which forwards to fixed PostHog hosts without cookies and answers CORS for the app's and the landing's origins only, without credentials; it answers 404 without `POSTHOG_KEY`. Server events (`user_signed_up` and `user_signed_in` from Better Auth's `events`, `first_task_created` from `TasksService`) and unexpected oRPC failures are queued, so no response waits for PostHog: posthog-node sends them in batches of 20 or every 5 seconds and flushes the rest when the runtime is disposed on shutdown. Events are queued only when the request carries a granted consent (the `AnalyticsConsent` reference, set per RPC request and per Better Auth hook); a failed batch is logged by name and never fails a request.

## Dates

A day is a `CalendarDate` (`YYYY-MM-DD`). The server cannot know the user's time zone, so `useToday()` reads the date in the browser (`useSyncExternalStore`, `undefined` during SSR, refreshed at local midnight and on tab focus). Calendar helpers work on UTC midnights, so they never cross a DST shift. The Upcoming list renders Overdue and every day from today to the end of the eighth week after the current one, then appends four more weeks whenever its end comes within a screen of the viewport, without end. Each loaded range has its own `tasks.list` query, so a range that is loading shows skeletons and a failed one shows Try again in place without hiding the tasks of the others; undated and overdue come from the first range. `useActiveDay` (a scroll tracker behind `useSyncExternalStore`, with ref callbacks on the sticky header and each day section) names the active day: the section at the top of the list, just under the header. The week strip and month label follow the active day's week; the arrows step one day (past the last rendered day the next weeks are appended first), the middle button names the active day (Today, Tomorrow, then e.g. Mon 9 Nov) and returns to today's section, and strip days scroll to their section, all landing just below the header (smooth unless the user prefers reduced motion). There is no `?week=` URL state.

## Shell

From `md` an icon rail is docked and the content keeps a rail-wide gutter; the content column is centered in the rest, so opening or collapsing the sidebar never moves it. From `xl` the owner's choice (full sidebar or rail) is docked and kept in the `soonlane-sidebar` cookie, read during SSR. Below `xl` the full sidebar opens over the content; phones use a drawer.

Inside the desktop app, `<html data-shell="desktop">` (set in the bundled page's `index.html`) turns on the `desktop:` variant: the rail, the sidebar and the phone bar leave 32px for the traffic lights and carry an `app-drag` strip that moves the window.

## Desktop app

`apps/desktop/src` mirrors the web app's layering in one module tree ([ADR 0005](docs/decisions/0005-desktop-app-layout.md), [ADR 0019](docs/decisions/0019-desktop-page-as-the-modules-presentation-layer.md)): the main process runs each module's `domain/`, `application/` and `infrastructure/`, and the page is its `presentation/` layer. `main.ts` builds `AppLive` from `platform/` (`DesktopConfig` with the `APP_URL` and `API_URL` baked in at build time, the `ManagedRuntime` and the Electrobun event helper; `platform/rpc` holds the page's RPC contract and its two clients). Modules: `window` opens windows on the bundled page at an `APP_PATHS` path in the hash (`openAppWindow`), keeps them on `views://app` with navigation rules, lends the page the token over Electrobun's typed RPC (a loopback WebSocket encrypted per webview), saves the main window's frame to `window-state.json` (ignoring a saved frame that no longer overlaps a display) and brings it forward after a sign-in; `navigation` sends web, mail and `webcal:` links to the system browser, the web app and the Todoist import included; `menu` sets the app menu; `identity` (`IdentityService`) keeps the token in the Keychain through `Bun.secrets`, one item per API origin, and signs in by binding a one-callback listener on `127.0.0.1` with a port the OS picks, opening `/desktop/sign-in` in the system browser and exchanging the code with the verifier it holds in memory; the listener closes after the callback, a new sign-in or 10 minutes. Signing out revokes the session, clears the Keychain item and tells every window. Deleting the account (`IdentityService.deleteAccount`) first asks `/get-session` whether the token is still the user's the dialog named, then calls `/delete-user` with the same token and, once the user is gone, forgets the token without revoking it; it holds the lock on token writes, so no sign-in stores another token meanwhile. Unlike the phone app ([ADR 0017](docs/decisions/0017-expo-mobile-app.md)), the Mac app keeps the token when it cannot confirm a deletion and asks the user to sign out, so the user learns the deletion was not confirmed. When the API asks for a fresh sign-in, the dialog starts one with `fresh=true`, the main process keeps the account in memory with that sign-in, and the page that loads with its token takes it once (`takeDeletionReturn`) to reopen the dialog, or to say nothing was deleted when the browser signed in to another account. A sign-in that replaces a token revokes the old one.

The bundled page starts at `src/view.tsx` and `src/router.tsx`, with the root route in `routes/` and each module's routes, screens and helpers in its `presentation/` folder (`identity`, `updates`, `quick-add`, and the page-only `shell` and `tasks`). It uses hash history (`views://` serves files, so a path would not survive a reload), the screens of `@soonlane/app` under the same `APP_PATHS` as the web app, a sign-in screen at `/sign-in`, and an oRPC link that sends the token as a bearer with `credentials: 'omit'`. Vite bakes in `APP_URL` (the Todoist import), `API_URL` and `LANDING_URL` (the landing, where the build info's release notes live). It asks the main process for the token at startup and keeps it in memory; every token change reloads the page, so each session starts with a new query client and router and no pending mutation of the previous account survives. A token the API no longer knows (`identity.me` returns no user) makes it sign out. Before any screen, the page asks `system.desktopSupport` once with its version; an app the API no longer serves shows only an update screen that links to the latest release. When a view fails for want of a connection (a network error, or a 502, 503 or 504), the window shows a no-connection screen instead of the error, which pings the API's `/health` every 5 seconds and reloads the routes once it answers; going back online reloads them at once. The page sends no browser analytics events yet.

The page and the main process share one `package.json`, so `effect` and the Electrobun main SDK resolve from page files too. Three guards keep the page out of the main process. `bun run typecheck` checks two programs: `tsconfig.main.json` has Bun types and no DOM (`WebWorker` only because Electrobun's main SDK reads `self`), and `tsconfig.page.json` has DOM and Vite types and no Bun or Node. Their one shared file is the RPC contract (`platform/rpc/page-rpc.types.ts`), written as plain `{ requests, messages }` objects so the page program needs no main SDK types. `tsconfig.json` only references the two programs, so editors and type-aware lint open each file in its own program, and `typecheck` names both, because `tsc` on the solution file checks nothing. The page build fails when its module graph reaches Effect, the Electrobun main SDK, `bun`, `bun:*`, `node:*` or a file under `src` that is not the page's (`pageBoundary` in `vite.config.ts`, which checks resolved paths). Lint (`oxlint.desktop.mts`) gives the page the web app's frontend rules and forbids it the same imports, allowing the contract as a type. Main-process files may not import React, the UI packages, `electrobun/view` or the page, and take from `@soonlane/app` only `app-paths` and types.

`quick-add` registers ⌥Space as an exclusive Carbon hot key (`RegisterEventHotKey`), as Todoist does: macOS hands the press only to Soonlane, so the frontmost app never types it, and no Accessibility access is needed. Carbon must run on the main thread and its handler must return a status, which a `bun:ffi` callback cannot, so a small C file (`platform/macos/carbon-hot-key.c`, copied into the app) does both and `cc` compiles it with TinyCC at launch (`carbon-hot-key.helper.ts`). A press opens Quick Add (`APP_PATHS.quickAdd`) on the bundled page in a small always-on-top window without a title bar on the display under the cursor, or brings the open one forward; it shares the main window's navigation rules, token and link handling (`openAppWindow`, `followNavigation`), and when signed out the shortcut brings the main window's sign-in screen forward instead. `updates` (`AppUpdates`) runs Electrobun's updater on signed stable builds: it checks the latest GitHub Release at launch and every 6 hours, downloads a newer version in the background and tells every window, whose page offers "Restart to update"; the update screen's "Update now" installs and restarts at once, and falls back to the release page when it cannot ([docs/release.md](docs/release.md#desktop-app)). `dock-badge` sets the Dock icon's badge through `bun:ffi` and the Objective-C runtime (`platform/macos`), since Electrobun has no badge API. Besides the token, the page sends the main process one RPC message, `pageMessage`, through the `sendToDesktop` host port of `@soonlane/app`, in three kinds the main process decodes with Effect Schema: `quick-add-done` closes the Quick Add window, `quick-add-suggestions` grows it while the "@" label suggestions are open, and `dock-badge` carries the count of open tasks overdue or due today, from any window. The page computes that count from the Today list in the TanStack Query cache (`syncDockBadge`); the main process clears the badge on sign-out ([ADR 0010](docs/decisions/0010-desktop-quick-add-and-dock-badge.md)).

## Linear connection

With `LINEAR_CLIENT_ID` and `LINEAR_CLIENT_SECRET` set, a signed-in user can link a Linear account, read only, from the user menu and keep it until they disconnect ([ADR 0021](docs/decisions/0021-linear-linked-for-pinned-issues.md)); pinning issues to tasks builds on it (see Linear pins). It is Better Auth's built-in `linear` provider (scope `read`), guarded like Todoist through `provider-link.handler.ts`, which names no provider: `createAuth` passes the configured link-only ones with their still-connected codes. "Connect Linear" opens the web `/linear` page (the desktop app opens it in the system browser), a browser-only route loader that reads `linear.status`, leaves a healthy connection alone, calls `linear.disconnect` for a lapsed one and then `/link-social`; Linear returns to `<API_URL>/api/auth/callback/linear`, which writes the `linear` row with the tokens encrypted, and then to `/linear?returned=true` (with `error=` when nothing was linked), which toasts "Linear connected" only when the status reads connected and goes to Upcoming. A callback neither updates a link-only row nor creates a second one for the same owner, so of two links racing the later one's tokens are revoked. `linear.status` answers `notConfigured`, `notConnected`, `connected` with the workspace's name (one GraphQL read of `viewer.organization.name`) or `lapsed`. A fresh access token is read without a lock; one permit per process covers refreshing and Disconnect. An access token (24 hours) within 5 minutes of expiry is refreshed through Better Auth's `refreshToken`, which writes the rotated pair back encrypted, in a fiber that holds the permit until the request settles (the `linear` provider's own token request gives up after 10 seconds), while the status call waits for it at most 15 seconds and otherwise reads lapsed; a failed refresh logs only Better Auth's code. Linear rotates the refresh token on each use, so a racing refresh or a Disconnect mid-refresh would lose the connection or leave a grant behind. A failed or timed-out refresh, a token the API cannot decrypt, or a 401 or `AUTHENTICATION_ERROR` from GraphQL reads as `lapsed`, and the menu offers Reconnect, which runs the same page. `linear.disconnect` revokes both tokens at `https://api.linear.app/oauth/revoke` with the token and its type hint alone in the form, counts 200, a 401 `Token not found` and a 400 for a token revoked before as gone, and deletes the row only then; other answers are logged with Linear's short `error` string; anything else keeps the row and fails, so the user can retry. Account deletion revokes both tokens best effort in the `linear-link` plugin's account delete hook, before the rows go. Tokens from a callback that stored no row are revoked by the callback's after hook.

### Linear pins

A task pins up to 10 Linear issues (`LINEAR_PINS_PER_TASK_MAX`); a subtask has its own. A `linear_pin` row keeps the task, Linear's issue id (primary key with the task), the identifier, title and URL as Linear read when the issue was pinned, and `pinned_at`; it has no owner column and is reached only through `ownedTasks` (`pinLinearIssue`, `unpinLinearIssue`, and `withRelations`, which loads every listed task's pins in one query, oldest first), which the `task-owner-scope` lint rule enforces for this table as for `task`. Deleting a task deletes its pins by cascade, and so does deleting the account; disconnecting Linear keeps them. Every task carries `linearPins`, which the row's badge reads without calling Linear. `linear.searchIssues` takes the picker's text: empty lists the user's open issues assigned to them (not completed or canceled, 50 most recently updated), an identifier such as `SOON-28` or an issue's link on `linear.app` reads that one issue, another link is answered without calling Linear, and other text runs Linear's `searchIssues` (20 results). `linear.listIssues` reads the current title and status of one task's pins (at most 10 ids) in one GraphQL request when an edit card opens. `linear.pin` reads the issue from Linear and stores it, inserting only while the task is the owner's and holds fewer than 10 pins, in one `INSERT … SELECT`; pinning a pinned issue refreshes its stored fields. `linear.unpin` needs no connection. Without a usable connection the reads answer `notConfigured`, `notConnected` or `lapsed` instead of issues, `pin` fails with `PRECONDITION_FAILED`, a full task with `CONFLICT`, and an issue Linear does not show the user with `NOT_FOUND`. Soonlane never writes to Linear.
