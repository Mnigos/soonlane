# Architecture

A Turborepo + Bun monorepo. One TanStack Start app serves the prerendered public site, the app UI with SSR, Better Auth at `/api/auth` and the oRPC API at `/api/rpc`, which a future desktop app will call too. Terms: [UBIQUITOUS_LANGUAGE.md](UBIQUITOUS_LANGUAGE.md). Decisions: [docs/decisions](docs/decisions).

## Package layering

```
apps/web ──► packages/auth ──► packages/db ──► packages/domain
    ├──────► packages/contracts ──────────────────┘
    └──────► packages/ui
tooling/* ◄── every workspace
```

Dependencies point one way. Packages are plain TypeScript and React without Effect; the web app owns Effect services and layers. Code moves into a package only when a second consumer needs it ([ADR 0002](docs/decisions/0002-package-layout.md)).

## Request flow

```
browser (orpcQuery + TanStack Query) or SSR (in-process client)
  → contract (packages/contracts)
    → /api/rpc: createRpcHandler (Origin check, context, RPCHandler)
      → router procedure (Effect) → service → port → adapter
```

`createRpcHandler` rejects any `Origin` other than the request's own and `AppConfig.trustedOrigins` (the base URL plus the Vercel branch and deployment hosts). Only `POST` reaches procedures. `system.health` returns `{ ok, db, version }`.

## Tasks

A task belongs to the user who created it, its owner (`task.owner_id`, cascade on user delete) and has a title, an optional description, a due date (`date`, no time zone), an optional due time (`time`), a priority 1 to 4 (default 4), `created_at` and a nullable `completed_at`. `tasks.list` takes `{ from, to, today }` from the browser and returns the open tasks due before `today` (overdue) and between `from` and `to`, ordered by time, priority, then age. Completing is optimistic in the TanStack Query cache and offers Undo (`tasks.uncomplete`). A task can carry a repeat rule (`repeat_unit`, `repeat_interval`, `repeat_anchor`, all set or all null, enforced by checks); completing a repeating task takes the browser's `today` and moves its due date to the next occurrence (`repeat-rule.helper`) instead of setting `completed_at`, with an update conditional on the due date the client showed (the stored one for older clients), and Undo sends the previous due date back. `tasks.update` replaces the title, description, due date and time and priority, sets the repeat rule or clears it on `null`, and keeps it when absent (tabs still on a bundle from before repeating tasks); the anchor moves to the saved due date only when the edit changes the date or the rule. Its optional `labelIds` replace the task's labels in the same transaction as the row, absent keeps them. The cache moves the edited task at once to the day, Overdue or range its new date belongs to, shows its new labels, and takes it out of a label view whose label it lost; a failed save puts it back everywhere. Reschedule on Overdue moves the shown overdue tasks to one day (`tasks.reschedule` takes their ids, skips completed and foreign ones and keeps due times), also optimistically; it changes only the due date, so a repeating task keeps its rule and anchor. `tasks.delete` removes a task for good in one `DELETE` filtered by owner (another user's task is NOT_FOUND), its `task_label` rows go by cascade, and the cache drops it at once, putting it back if the request fails. `tasks.listCompleted` takes `{ from, to }`, the browser's local midnights around its today, and returns the tasks completed in that half-open range, last completed first; Today shows them under Completed. Every task the API returns carries its labels, loaded by task ids in one query per list query (two for `tasks.list`); advancing a repeating task updates the same row, so it keeps its labels.

## Labels

A label belongs to the owner (`label.owner_id`, cascade on user delete) and has a name and an optional color, one of Todoist's 20 palette colors as a kebab-case key (`LABEL_COLORS`, e.g. `sky-blue`; no color means the default color in the UI). Names are trimmed, 1 to 60 characters and unique per owner ignoring case, enforced by a unique index on `(owner_id, lower(name))`: `labels.create` and `labels.update` write without checking first and the service maps the index violation to CONFLICT, so concurrent creates and renames to a taken name also return CONFLICT. `task_label` joins tasks and labels (cascade on both), so deleting a label takes it off every task. `tasks.create` and `tasks.update` take optional `labelIds` (no duplicates) and write the task and its labels in one transaction, leaving out ids that are not the owner's labels; on `tasks.update` they replace the task's labels, and an empty list takes them all off. `tasks.assignLabel` and `tasks.unassignLabel` are idempotent and write only when the task and the label both belong to the owner; another user's task or label is NOT_FOUND. Labels are sorted by lower-cased name, then age. `labels.list` also counts each label's open tasks (`openTaskCount`) in the same query; creating, editing, completing and uncompleting a task, and renaming or deleting a label, refresh it along with the task lists. The sidebar lists the labels, links each to `/app/labels/$name` and adds, renames and deletes them.

The label view at `/app/labels/$name` finds the label by name ignoring case in `labels.list` (its loader fills the tab title) and shows a not-found page for any other name. `tasks.listByLabel` takes `{ labelId, today }` and returns the label's open tasks with any due date in the `tasks.list` shape, overdue before `today` and scheduled from it; a label that is not the owner's is NOT_FOUND. Both procedures share the `tasks` query key, so completing a task and the refreshes after a change reach every task list.

## Public site

`routes.ts` splits the tree into two pathless layouts ([ADR 0008](docs/decisions/0008-public-site-inside-the-web-app.md)). The `session` layout wraps `/app`, `/login` and the desktop sign-in routes: its `beforeLoad` calls `identity.me` and its `head` adds `noindex, nofollow`. The `site` layout wraps `/`, `/privacy`, `/terms`, `/changelog`, `/blog` and `/blog/$slug` and never reads the session, so those pages make no request to `/api/auth` or `/api/rpc`. The header and the landing call to action show "Open app" instead of "Log in" and "Get started" when the browser holds the `soonlane-signed-in` hint cookie: a head script marks `<html data-signed-in>` before first paint and the `signed-in:` Tailwind variant picks between the two variants in the prerendered HTML.

TanStack Start prerenders the public pages and `/sitemap.xml` during `vite build` (`prerender` and `pages` in `apps/web/vite.config.ts`; `isPublicPath` keeps `/app`, `/login`, `/desktop`, `/api`, `/calendar`, `/robots.txt` and `/today` out of the crawl). Nitro writes them to `.vercel/output/static`, which Vercel serves before the `__server` function, and the build needs no env vars. Legal pages are MDX in `modules/site/content` with `title`, `description` and `updated` frontmatter, compiled by content-collections into `.content-collections/generated` (imported as `content-collections`; `bun install` and `typecheck` generate it). Blog posts are MDX in `modules/blog/content`; a production build (`VERCEL_ENV=production`) skips drafts and future-dated posts in the collection transform, so their text never reaches the output, and other builds mark them with a `published` flag that shows the Draft label and `noindex`. The post data is a chunk of its own that only the blog routes load. `/blog` and `/blog/rss.xml` are in `pages`; posts are reached by crawling `/blog`, and the sitemap lists published posts only. Before `vite build`, `apps/web/scripts/og-images.tsx` draws a 1200×630 share image for every post in the generated data (satori and resvg, devDependencies only) into `public/og/blog/<slug>.png`, which is gitignored; a post's own `image` frontmatter replaces it.

Canonical links, Open Graph URLs and the sitemap use the constant `SITE_URL` (`https://soonlane.com`), never the request host. `/robots.txt` is rendered per request: on `soonlane.com` it allows `/`, disallows `/app`, `/api/`, `/calendar/`, `/login` and `/desktop/` and points to the sitemap; on every other host (previews, `soonlist.vercel.app`, `www`) it disallows everything. A new public page needs an entry in `pages` and in `SITEMAP_ENTRIES`; blog posts need neither.

A task can carry a goal: `goal_target` (1 to 10,000), an optional `goal_unit` (up to 24 characters) and `goal_progress`, the progress of the current occurrence (0 to the target; check constraints keep the three consistent). `tasks.logProgress` takes the amount with the browser's `today` and the due date it showed, and applies it in one `UPDATE` computed in SQL on the row it locks, so concurrent logs never lose an increment: progress is clamped to 0 and the target. On a task that does not repeat, reaching the target sets `completed_at`, and a log that takes it back below the target clears it again, which is how Undo works there. On a repeating task, reaching the target moves the due date to the next occurrence and resets the progress to 0 in the same statement, only while the task still has the due date the client showed; otherwise the log counts toward the current occurrence and nothing advances. Completing a repeating goal task with the circle resets its progress the same way; on a task that does not repeat the circle never touches progress. The response carries `logged`, the amount the server applied after clamping, and `completed` when this log completed the task: the due date it was completed on and the progress before the log. `completed` decides the "Task completed" toast and the `task_completed` event. Undo of a repeating task, from a log or the circle, calls `tasks.uncomplete` with the previous due date and progress (clamped to the target, ignored without a goal); the circle takes that progress from the cached row. Undo of a task that does not repeat logs `-logged`. Logging is optimistic in every task list. A log's own refresh waits until no other log is pending; refreshes from other mutations are not held back. `tasks.update` takes an optional `goal`: absent keeps the goal and its progress, `null` clears target, unit and progress, and a new target clamps the progress to it, all on the row it locks first, so the progress check never fails. An edit that leaves an open task's progress at its target (a lower new target, or the kept one of a task reopened at its target) completes it like a log, so no open task sits at its target after an edit: a task that does not repeat gets `completed_at`, a repeating one moves to its next occurrence from the edited due date (with the browser's `today`) and starts at 0. The response's `completed` then carries the due date it completed on, the previous progress and the previous goal, and Undo sends all three back to `tasks.uncomplete`, which restores the goal before clamping the progress to it.

## Calendar subscription

Each account can have one private calendar link ([ADR 0011](docs/decisions/0011-private-calendar-subscription-link.md)). `calendar.createSubscription` draws a 256-bit token, stores only its SHA-256 in `calendar_subscription` (keyed by `owner_id`, cascade on user delete) and returns `<baseUrl>/calendar/<token>.ics` once; creating again replaces the row, so the old link stops working. `calendar.getSubscription` returns only the creation time, and `calendar.revokeSubscription` deletes the row. `GET /calendar/{$token}.ics` needs no session: a malformed, unknown or revoked token gets an empty 404, a known one the owner's open tasks from `TasksService.listOpen` as `text/calendar`, with `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow` and `Referrer-Policy: no-referrer`. Each task is one event on its due date: all day without a due time, a floating local time with a 30-minute duration and an alarm at its start with one; the summary is the title, the description the task's description and labels, the URL `/app`, the UID `<taskId>@soonlane.com`. The feed asks for a refresh every 15 minutes. Any other method on that path, and any other path under `/calendar/`, gets the same empty 404 with the same headers, so a link never reaches the app's HTML pages. The route catches every failure, logs only the error name and never the URL or the token.

## Sign-in

Better Auth with Google at `/api/auth`, configured by `createAuth` in `packages/auth` and built once by `BetterAuthLive` from `AppConfig` and `Db` ([ADR 0003](docs/decisions/0003-better-auth-in-a-package-behind-an-effect-layer.md)). Any Google account with a verified address can sign up and gets its own tasks; a non-empty `ALLOWED_EMAILS` limits new accounts to those addresses and leaves existing ones alone ([ADR 0009](docs/decisions/0009-open-sign-in.md)). "Delete account" in the user menu calls Better Auth's `/delete-user`, which needs a session younger than a day and removes the user with its sessions, accounts and tasks. Better Auth rate limits `/api/auth` per client IP (`x-forwarded-for`, which Vercel overwrites) in the `rate_limit` table: 100 requests a minute, 10 for Google sign-in and each desktop sign-in step, 5 deletions an hour. Every new or refreshed session also sets `soonlane-signed-in=1` (not HttpOnly, no user data) so static pages can show "Open app"; sign-out and deletion clear it. Google accepts only the production and localhost redirect URIs, so on Vercel production and previews the `oAuthProxy` plugin sends a preview's sign-in through the production callback and back; both sides share `OAUTH_PROXY_SECRET` (or `AUTH_SECRET`). Local development signs in directly. Details: [docs/deploy-vercel.md](docs/deploy-vercel.md).

The desktop app signs in through the system browser ([ADR 0007](docs/decisions/0007-desktop-sign-in-through-the-system-browser.md)). The `desktopSignIn` plugin in `packages/auth` lets the signed-in browser trade the app's PKCE challenge for a one-time code (2 minutes, stored hashed in `verification`) at `/desktop/sign-in`, which returns to the app through `soonlane://sign-in?code=…`. The window's `/desktop/callback` exchanges the code and the app's verifier for a session of its own, so signing out in the app leaves the browser signed in. The desktop session keeps the browser session's `createdAt`, so it is never fresh enough for account deletion when the browser session is not; `/desktop/sign-in?fresh=true` goes through Google first.

## Database

Neon Postgres through `pg` and Drizzle. `Db` owns one pool per runtime (5 connections, 10 s `query_timeout`, an `error` listener); `Db.run` is the only place that creates `DbError`. Logs carry error names only, because driver errors embed SQL parameters such as session tokens. The Vercel build runs the migrator first against the environment's own Neon branch (`main` for production, `preview` for previews and local).

## Server boundary

Server-only code never reaches the client bundle: `platform/`, `application/`, `infrastructure/`, server-suffixed files and `routes/api.*`. TanStack Start import protection in `apps/web/vite.config.ts` fails the build on a leak; it also denies `@soonlane/auth/server`, `@soonlane/db`, `pg`, `drizzle-orm` and `posthog-node` by specifier, and excludes the four browser-safe oRPC client files in `platform/rpc`. After a build, `apps/web/.vercel/output/static/assets` must not contain `drizzle`, `pg`, `betterAuth(`, `drizzleAdapter`, `oauth-proxy`, `effect/`, `ManagedRuntime`, `posthog-node`, `captureImmediate` or service names. Server route handlers (`/api/auth/$`, `/ingest/$`, `/calendar/{$token}.ics`, `/calendar/$`) reach the runtime only from `server.handlers`, which TanStack Start keeps out of the client bundle.

## Analytics

PostHog (EU) receives product events, session replays and exceptions; the tracking plan is [docs/analytics.md](docs/analytics.md). Everything hangs on `VITE_POSTHOG_KEY`: without it posthog-js is never downloaded, no consent banner appears, the server's `Analytics` is a no-op and `/ingest` answers 404. With it, each visitor's answer in the `soonlane-consent` cookie decides: nothing before an answer, full analytics and masked replay when granted, cookieless anonymous events when denied or under Global Privacy Control; posthog-js never runs on `/desktop/*`. The browser sends through the first-party `/ingest` proxy (a server route that forwards to fixed PostHog hosts without the app's cookies). Server events (`user_signed_up` and `user_signed_in` from Better Auth's `events`, `first_task_created` from `TasksService`) and unexpected oRPC failures go out with `captureImmediate` before the response, the events only when the request carries a granted consent (the `AnalyticsConsent` reference, set per RPC request and per Better Auth hook), because the function can freeze right after it; a failed delivery is logged by name and never fails the request.

## Dates

A day is a `CalendarDate` (`YYYY-MM-DD`). The server cannot know the user's time zone, so `useToday()` reads the date in the browser (`useSyncExternalStore`, `undefined` during SSR, refreshed at local midnight and on tab focus). Calendar helpers work on UTC midnights, so they never cross a DST shift. The Upcoming list renders Overdue and every day from today to the end of the eighth week after the current one, then appends four more weeks whenever its end comes within a screen of the viewport, without end. Each loaded range has its own `tasks.list` query, so a range that is loading shows skeletons and a failed one shows Try again in place without hiding the tasks of the others; overdue comes from the first range. `useActiveDay` (a scroll tracker behind `useSyncExternalStore`, with ref callbacks on the sticky header and each day section) names the active day: the section at the top of the list, just under the header. The week strip and month label follow the active day's week; the arrows step one day (past the last rendered day the next weeks are appended first), the middle button names the active day (Today, Tomorrow, then e.g. Mon 9 Nov) and returns to today's section, and strip days scroll to their section, all landing just below the header (smooth unless the user prefers reduced motion). There is no `?week=` URL state.

## Shell

From `md` an icon rail is docked and the content keeps a rail-wide gutter; the content column is centered in the rest, so opening or collapsing the sidebar never moves it. From `xl` the owner's choice (full sidebar or rail) is docked and kept in the `soonlane-sidebar` cookie, read during SSR. Below `xl` the full sidebar opens over the content; phones use a drawer.

Inside the desktop app, `<html data-shell="desktop">` (set by its preload) turns on the `desktop:` variant: the rail, the sidebar and the phone bar leave 32px for the traffic lights and carry an `app-drag` strip that moves the window.

## Desktop app

`apps/desktop/src` mirrors the web app's layering ([ADR 0005](docs/decisions/0005-desktop-app-layout.md)). `main.ts` builds `AppLive` from `platform/` (`DesktopConfig` with the `APP_URL` baked in at build time, the `ManagedRuntime`, the Electrobun event helper). Modules: `window` opens the main window and saves its frame to `window-state.json`, ignoring a saved frame that no longer overlaps a display; `navigation` keeps the window on the app's exact origin and sends other web and mail links to the system browser; `menu` sets the app menu; `sign-in` opens the desktop sign-in in the system browser with the challenge of its pending verifier (a new one when none is pending) and, on a `soonlane://` link, loads `/desktop/callback` with the code and that verifier. macOS delivers `soonlane://` links only to a copy of the app in `/Applications`.

`quick-add` registers ⌥Space with Electrobun's `GlobalShortcut` and asks macOS for Accessibility access, which the shortcut needs to work in other apps. A press opens `/app/quick-add` in a small always-on-top window without a title bar on the display under the cursor, or brings the open one forward; it shares the main window's preload, navigation rules and link handling (`openAppWindow`, `followNavigation`). `dock-badge` sets the Dock icon's badge through `bun:ffi` and the Objective-C runtime (`platform/macos`), since Electrobun has no badge API. The page talks to the main process only through the preload's `__electrobunSendToHost`, with two messages decoded by Effect Schema: `quick-add-done` closes the Quick Add window, and `dock-badge` carries the count of open tasks overdue or due today. The web app computes that count from the Today list in the TanStack Query cache (`syncDockBadge`), and sends 0 when sign-out clears the cache ([ADR 0010](docs/decisions/0010-desktop-quick-add-and-dock-badge.md)).
