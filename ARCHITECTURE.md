# Architecture

A Turborepo + Bun monorepo. A TanStack Start app, built as one Bun server on Railway, serves the prerendered public site and the app UI with SSR; the API on Railway serves Better Auth at `/api/auth`, the oRPC API at `/api/rpc` and the calendar feed, and is the only code that reaches the database. The browser calls the API host directly with credentials; the session cookie covers both hosts through the environment's shared domain. Terms: [UBIQUITOUS_LANGUAGE.md](UBIQUITOUS_LANGUAGE.md). Decisions: [docs/decisions](docs/decisions).

## Package layering

```
apps/api ──► packages/auth ──► packages/db ──► packages/domain
    ├──────► packages/contracts ──────────────────┘
    └──────► packages/analytics (root) ──► packages/domain
apps/web ──► packages/auth (root, client), packages/contracts, packages/domain, packages/ui
    ├──────► packages/app ──► packages/contracts, packages/domain, packages/ui
    └──────► packages/analytics ──► packages/ui, packages/domain
tooling/* ◄── every workspace
```

Dependencies point one way. Packages are plain TypeScript and React without Effect; the API owns the Effect services and layers. Code moves into a package only when a second consumer needs it ([ADR 0002](docs/decisions/0002-package-layout.md)). A planned Expo app, `apps/mobile`, will use only the DOM-free hooks and helpers of `packages/app` with `packages/contracts` and `packages/domain`, and never `packages/ui` ([ADR 0017](docs/decisions/0017-expo-mobile-app.md)).

## Request flow

```
browser (orpcQuery + TanStack Query, VITE_API_URL) ─┐
SSR (rpc.client.server, API_INTERNAL_URL) ──────────┤
  → API: withCors → withClientIp → createRpcHandler (Origin check, context, RPCHandler)
    → router procedure (Effect) → service → port → adapter
```

One `RPCLink` serves the browser and SSR; `orpcQuery` from `@soonlane/app` calls through it. The browser calls the API's public origin, `VITE_API_URL` (build time), with `credentials: 'include'`, and so does the Better Auth client. SSR calls the API directly at the runtime variable `API_INTERNAL_URL` and sends only this environment's Better Auth `session_token`, `session_data` and `dont_remember` cookies (`<prefix>.<name>`, `__Secure-<prefix>.<name>` on https, prefix from `VITE_AUTH_COOKIE_PREFIX`) and `<prefix>.consent`, by exact name, the visitor's IP in `x-soonlane-visitor-ip` (Railway's `X-Real-IP`, or `CF-Connecting-IP` when that address is a Cloudflare edge, through `resolveEdgeIp` from `@soonlane/auth/client-ip`, the same rule the API applies; the socket address locally) and `API_PROXY_SECRET` in `x-soonlane-proxy-secret`. Every `Set-Cookie` of the answer goes onto the page's response, so a session refreshed by `identity.me` sticks.

The API's entry answers CORS for `/api/auth` and `/api/rpc` (`withCors`). A preflight from an origin in `TRUSTED_ORIGINS` gets 204 with that exact origin, credentials, `GET, POST`, `content-type` (all the oRPC link and the Better Auth client send) and a two-hour cache. The desktop app's bundled page (`DESKTOP_PAGE_ORIGIN`, `views://app`) gets its exact origin without credentials and may also send `authorization`, for its bearer token, and its responses lose any `Set-Cookie`; it is not in `TRUSTED_ORIGINS` (where `views://app` would parse to the origin `null` anyway), so it is never a return address and never receives the cookie. Any other origin gets 403, including other `soonlane.com` hosts and the API's own. Other requests with an allowed `Origin` carry the same headers, on errors too; any other `Origin` gets 403; a request without `Origin` (SSR, Google's redirect back, the desktop app's main process) passes to Better Auth and oRPC, whose own origin checks stay on. The RPC handler repeats the origin check before it looks up the session and refuses a request from the desktop page that carries a cookie.

`createRpcHandler` also rejects any `Origin` outside `TRUSTED_ORIGINS`, except the desktop page's when it carries no cookie. Only `POST` reaches procedures. A session lookup that refreshes or deletes the session cookie returns its `Set-Cookie` values (`getSession` with `returnHeaders`), and the handler appends each to that request's response. `system.health` returns `{ ok, db, version, commit }`.

## Client IP

The API's HTTP entry (`withClientIp`) settles one address per `/api/auth` and `/api/rpc` request and writes it into `x-soonlane-client-ip`, the only header Better Auth reads; an incoming copy is dropped. With `x-soonlane-proxy-secret` the request comes from the web server: the secret is compared in constant time (both sides hashed), a wrong one gets 403 and a log line without the value, and the right one makes the API take `x-soonlane-visitor-ip` if it is one valid address, else 400. Without the secret header the API takes Railway's `X-Real-IP` (missing or invalid: 400); when that address is in Cloudflare's published ranges (the proxied production host), it takes `CF-Connecting-IP` instead (one valid address, else 400). A client that reaches Railway directly shows its own address in `X-Real-IP`, so a forged `CF-Connecting-IP` is ignored. The secret and visitor headers never reach a handler or a log. `/health` and the calendar feed skip this step.

## Tasks

A task belongs to the user who created it, its owner (`task.owner_id`, cascade on user delete) and has a title, an optional description, an optional due date (`date`, no time zone; a task without one has no due time and no repeat rule, which the contract checks), an optional due time (`time`), a priority 1 to 4 (default 4), `created_at` and a nullable `completed_at`. `tasks.list` serves every view of open tasks. It takes the browser's `today` and optional filters: `from` and `to` together limit the scheduled tasks to a range (without them every task due from `today` on is scheduled), `labelId` keeps the tasks with that label and `projectId` the tasks in that project; every filter given applies. It returns the open tasks without a due date (undated; without a label or project filter only those without a project, the Inbox), those due before `today` (overdue) and the scheduled ones, read in one query in the order `TASK_DAY_ORDER` in `@soonlane/domain` defines (date with undated last, time with untimed last, priority, then age). Completing is optimistic in the TanStack Query cache and offers Undo (`tasks.uncomplete`). A task can carry a repeat rule (`repeat_unit`, `repeat_interval`, `repeat_anchor`, all set or all null, enforced by checks); completing a repeating task takes the browser's `today` and moves its due date to the next occurrence (`repeat-rule.helper`) instead of setting `completed_at`, with an update conditional on the due date the client showed (the stored one for older clients), and Undo sends the previous due date back. `tasks.edit` writes only the fields it carries, so a tab with an older copy of the task does not write it back over changes made elsewhere: absent keeps a field, `null` clears the description, due date, due time, repeat rule, goal or project, and no due date also clears the time and the rule; two edits of the same field are last write wins. An edit that carries neither a due date nor a rule leaves the schedule columns alone; one that carries a due date snaps it and moves the anchor to it only when it changes the date or the rule. A version check was rejected: it needs a migration and a bump on every write path, and a menu change should apply, not be refused. `tasks.update` stays for desktop apps that bundle a UI from before `tasks.edit` until the API can ask them to update (SOON-152): it replaces the title, description, due date and time and priority (an absent description, date or time becomes `null`), keeps an absent repeat rule, goal or project, and runs as the same edit. Optional `labelIds` replace the task's labels in the same transaction as the row, absent keeps them. The cache moves the edited task at once to the day, Overdue or range its new date belongs to, shows its new labels, and takes it out of a label view whose label it lost; a failed save puts it back everywhere. Reschedule on Overdue moves the shown overdue tasks to one day (`tasks.reschedule` takes their ids, skips completed and foreign ones and keeps due times), also optimistically; it changes only the due date, so a repeating task keeps its rule and anchor. `tasks.delete` removes a task for good in one `DELETE` filtered by owner (another user's task is NOT_FOUND), its `task_label` rows go by cascade, and the cache drops it at once, putting it back if the request fails. `tasks.listCompleted` takes `{ from, to }`, the browser's local midnights around its today, and returns the tasks completed in that half-open range, last completed first; Today shows them under Completed. `tasks.search` takes `{ query }` (trimmed, 1 to 100 characters) and returns the owner's tasks whose title or description contains every word of it, case-insensitive and with `%`, `_` and `\` matched as typed: open tasks in day order, then completed ones, last completed first, at most 50 with `hasMore` for the rest. Search (`/app/search`) keeps the query in React state only and sends it 300 ms after the last keystroke; every task change refetches its results too. The search palette (⌘K) runs the same search and hands its query to the page in navigation state, never in the URL; `tasks.get` loads one of the owner's tasks for its Recent list. Every task the API returns carries its labels and its project, each loaded in one query per list query; advancing a repeating task updates the same row, so it keeps its labels.

## Labels

A label belongs to the owner (`label.owner_id`, cascade on user delete) and has a name and an optional color, one of Todoist's 20 palette colors as a kebab-case key (`LABEL_COLORS`, e.g. `sky-blue`; no color means the default color in the UI). Names are trimmed, 1 to 60 characters and unique per owner ignoring case, enforced by a unique index on `(owner_id, lower(name))`: `labels.create` and `labels.update` write without checking first and the service maps the index violation to CONFLICT, so concurrent creates and renames to a taken name also return CONFLICT. `task_label` joins tasks and labels (cascade on both), so deleting a label takes it off every task. `tasks.create`, `tasks.edit` and `tasks.update` take optional `labelIds` (no duplicates) and write the task and its labels in one transaction, leaving out ids that are not the owner's labels; on an edit they replace the task's labels, and an empty list takes them all off. `tasks.assignLabel` and `tasks.unassignLabel` are idempotent and write only when the task and the label both belong to the owner; another user's task or label is NOT_FOUND. Labels are sorted by lower-cased name, then age. `labels.list` also counts each label's open tasks (`openTaskCount`) in the same query; creating, editing, completing and uncompleting a task, and renaming or deleting a label, refresh it along with the task lists. The sidebar lists the labels, links each to `/app/labels/$name` and adds, renames and deletes them.

The label view at `/app/labels/$name` finds the label by name ignoring case in `labels.list` (its loader fills the tab title) and shows a not-found page for any other name. It calls `tasks.list` with `{ labelId, today }`, which returns the label's open tasks, undated, overdue before `today` and scheduled from it; a label that is not the owner's is NOT_FOUND. The Inbox view (`/app/inbox`) asks with Today's input (`getTodayListInput`) and shows only `undated`, so it shares Today's cache entry. Every view caches its list under the one `tasks.list` key, so completing, editing, logging progress and rescheduling update every task list at once, and the refreshes after a change reach them all.

## Projects

A project belongs to the owner (`project.owner_id`, cascade on user delete) and has a name: trimmed, 1 to 120 characters and unique per owner ignoring case, enforced by a unique index on `(owner_id, lower(name))`, which `projects.create` and `projects.update` map to CONFLICT like labels. A task has at most one project (`task.project_id`, nullable); deleting a project sets it to null on its tasks (`ON DELETE SET NULL`), so the tasks stay. `tasks.create`, `tasks.edit` and `tasks.update` take an optional `projectId`; one that is missing or not the owner's is NOT_FOUND and nothing is written, and so is a project deleted between that check and the write (the foreign key violation maps to the same error). On `tasks.update` an absent `projectId` keeps the project and `null` clears it, like the repeat rule and the goal, so edits that do not show the project never drop it. `projects.list` is sorted like labels and counts each project's open tasks (`openTaskCount`). `tasks.list` with `{ projectId, today }` returns the project's open tasks; a project that is not the owner's is NOT_FOUND. The sidebar lists the projects above the labels and adds, renames and deletes them; the project view at `/app/projects/$name` works like the label view, and its Add task row puts each new task in the project. Creating, editing, completing and deleting a task and renaming or deleting a project refresh `projects.list` along with the task lists, and the cache places an edited task in a project view only when it has that project.

## Public site

`routes.ts` splits the tree into two pathless layouts ([ADR 0008](docs/decisions/0008-public-site-inside-the-web-app.md)). The `session` layout wraps `/app`, `/login` and the desktop sign-in routes: its `beforeLoad` calls `identity.me` and its `head` adds `noindex, nofollow`. The `site` layout wraps `/`, `/privacy`, `/terms`, `/changelog`, `/blog` and `/blog/$slug` and never reads the session, so those pages make no request to `/api/auth` or `/api/rpc`. The header and the landing call to action show "Open app" instead of "Log in" and "Get started" when the browser holds the `<prefix>.signed_in` hint cookie (`soonlane.signed_in` in production): a head script marks `<html data-signed-in>` before first paint and the `signed-in:` Tailwind variant picks between the two variants in the prerendered HTML.

TanStack Start prerenders the public pages during `vite build` (`prerender` and `pages` in `apps/web/vite.config.ts`; `isPrerenderedPath` keeps `/app`, `/login`, `/desktop`, `/api`, `/calendar`, `/robots.txt`, `/today`, `/health`, `/blog/rss.xml` and `/sitemap.xml` out of the crawl), and the build needs no env vars. It writes them into `.output/public` after Nitro has listed its static files, so Nitro never serves them. The hosting behaviour lives in `modules/hosting` as Start request middlewares, registered in `src/start.ts` after Start's CSRF check for server functions, which Start drops once a start instance exists and which also accepts the host's `https://` origin because Railway's edge ends TLS: `prerendered-pages.middleware.ts` answers each `<path>/index.html` from disk, `compression.middleware.ts` gzips text responses outside development (Nitro's own static files are precompressed at build time), and `error-cache.middleware.ts` gives every 4xx and 5xx, a missing asset's 404 included, `no-store`. The Nitro config adds `public, max-age=31536000, immutable` to files under `/assets/` that exist and `no-cache` to every other success. The feeds are rendered per request, which keeps the content types their routes set. `/health` (`routes/health.route.ts`) answers `{ ok, environment, commit }` without the API, for Railway's health check. `bun run build` ends with `scripts/check-server.ts`, which starts the built server from a copy outside the repo and checks robots per host, a prerendered page read from disk, compression, both asset cases and `/health`. Legal pages are MDX in `modules/site/content` with `title`, `description` and `updated` frontmatter, compiled by content-collections into `.content-collections/generated` (imported as `content-collections`; `bun install` and `typecheck` generate it). Blog posts are MDX in `modules/blog/content`; a production build (`APP_ENV=production`) skips drafts and future-dated posts in the collection transform, so their text never reaches the output, and other builds mark them with a `published` flag that shows the Draft label and `noindex`. The post data is a chunk of its own that only the blog routes load. `/blog` is in `pages`; posts are reached by crawling `/blog`, and the sitemap lists published posts only. Before `vite build`, `apps/web/scripts/og-images.tsx` draws a 1200×630 share image for every post in the generated data (satori and resvg, devDependencies only) into `public/og/blog/<slug>.png`, which is gitignored; a post's own `image` frontmatter replaces it.

Canonical links, Open Graph URLs and the sitemap use the constant `SITE_URL` (`https://soonlane.com`), never the request host. `/robots.txt` is rendered per request: on `soonlane.com` it allows `/`, disallows `/app`, `/api/`, `/calendar/`, `/login` and `/desktop/` and points to the sitemap; on every other host (staging, Railway's generated hosts, `www`) it disallows everything. A new public page needs an entry in `pages` and in `SITEMAP_ENTRIES`; blog posts need neither.

A task can carry a goal: `goal_target` (1 to 10,000), an optional `goal_unit` (up to 24 characters) and `goal_progress`, the progress of the current occurrence (0 to the target; check constraints keep the three consistent). `tasks.logProgress` takes the amount with the browser's `today` and the due date it showed, and applies it in one `UPDATE` computed in SQL on the row it locks, so concurrent logs never lose an increment: progress is clamped to 0 and the target. On a task that does not repeat, reaching the target sets `completed_at`, and a log that takes it back below the target clears it again, which is how Undo works there. On a repeating task, reaching the target moves the due date to the next occurrence and resets the progress to 0 in the same statement, only while the task still has the due date the client showed; otherwise the log counts toward the current occurrence and nothing advances. Completing a repeating goal task with the circle resets its progress the same way; on a task that does not repeat the circle never touches progress. The response carries `logged`, the amount the server applied after clamping, and `completed` when this log completed the task: the due date it was completed on and the progress before the log. `completed` decides the "Task completed" toast and the `task_completed` event. Undo of a repeating task, from a log or the circle, calls `tasks.uncomplete` with the previous due date and progress (clamped to the target, ignored without a goal); the circle takes that progress from the cached row. Undo of a task that does not repeat logs `-logged`. Logging is optimistic in every task list. A log's own refresh waits until no other log is pending; refreshes from other mutations are not held back. `tasks.edit` and `tasks.update` take an optional `goal`: absent keeps the goal and its progress, `null` clears target, unit and progress, and a new target clamps the progress to it, all on the row it locks first, so the progress check never fails. An edit that leaves an open task's progress at its target (a lower new target, or the kept one of a task reopened at its target) completes it like a log, so no open task sits at its target after an edit: a task that does not repeat gets `completed_at`, a repeating one moves to its next occurrence from the edited due date (with the browser's `today`) and starts at 0. The response's `completed` then carries the due date it completed on, the previous progress and the previous goal, and Undo sends all three back to `tasks.uncomplete`, which restores the goal before clamping the progress to it.

## Calendar subscription

Each account can have one private calendar link ([ADR 0011](docs/decisions/0011-private-calendar-subscription-link.md)). `calendar.createSubscription` draws a 256-bit token, stores only its SHA-256 in `calendar_subscription` (keyed by `owner_id`, cascade on user delete) and returns `<API_URL>/calendar/<token>.ics` (`https://api.soonlane.com/...`) once; creating again replaces the row, so the old link stops working. `calendar.getSubscription` returns only the creation time, and `calendar.revokeSubscription` deletes the row. The API's `GET /calendar/<token>.ics` needs no session: a malformed, unknown or revoked token gets an empty 404, a known one the owner's open tasks with a due date from `TasksService.listOpen` as `text/calendar`, with `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow` and `Referrer-Policy: no-referrer`. Each task is one event on its due date: all day without a due time, a floating local time with a 30-minute duration and an alarm at its start with one; the summary is the title, the description the task's description and labels, the URL `APP_URL` + `/app` on the web app, the UID `<taskId>@soonlane.com`. The feed asks for a refresh every 15 minutes. Any other method on that path, and any other path under `/calendar/`, gets the same empty 404 with the same headers, and the web app has no `/calendar` routes. The handler catches every failure, logs only the error name and never the URL or the token.

## Sign-in

Better Auth with Google at `/api/auth`, configured by `createAuth` in `packages/auth` and built once by `BetterAuthLive` from `AppConfig` and `Db` ([ADR 0003](docs/decisions/0003-better-auth-in-a-package-behind-an-effect-layer.md)). Any Google account with a verified address can sign up and gets its own tasks; a non-empty `ALLOWED_EMAILS` limits new accounts to those addresses and leaves existing ones alone ([ADR 0009](docs/decisions/0009-open-sign-in.md)). "Delete account" in the user menu calls Better Auth's `/delete-user`, which needs a session younger than a day and removes the user with its sessions, accounts and tasks. Better Auth runs on the API and rate limits `/api/auth` per client IP (see Client IP) in the `rate_limit` table: 100 requests a minute, 10 for Google sign-in, linking Todoist and each desktop sign-in step, 5 deletions an hour. Its base URL is the API's origin (`API_URL`), so Google returns to `https://api.soonlane.com/api/auth/callback/google` (staging `https://api.staging.soonlane.com/...`). Cookies carry the environment's prefix (`AUTH_COOKIE_PREFIX`: `soonlane`, `soonlane-staging`) and its domain (`AUTH_COOKIE_DOMAIN`: `soonlane.com`, `staging.soonlane.com`), so the session (`__Secure-soonlane.session_token`) reaches the web app and the API ([ADR 0013](docs/decisions/0013-three-hosts-on-railway.md)). Every new or refreshed session also sets `<prefix>.signed_in=1` with the session cookie's attributes but not HttpOnly (no user data), so static pages can show "Open app"; sign-out and deletion clear it. The `returnAddresses` plugin (`packages/auth/src/return-address.handler.ts`) runs before Better Auth routes a request and accepts return addresses (`callbackURL`, `errorCallbackURL`, `newUserCallbackURL`, `redirectTo` in the body, every `callbackURL` in the query) only as absolute URLs on a `TRUSTED_ORIGINS` origin, and `/sign-in/social` must carry a `callbackURL` in its body; anything else gets 400. Better Auth's errors redirect to the web `/login?error=…` (`onAPIError.errorURL`). Google only signs in; Todoist, when configured, is only linked to a signed-in account (`/sign-in/social` refuses it, `/link-social` accepts nothing else, takes no scopes or extra parameters and refuses while the user has a `todoist` row). Provider tokens are stored encrypted with `AUTH_SECRET`, and the endpoints that return them to the browser (`/get-access-token`, `/refresh-token`, `/account-info`) are disabled, as is `/unlink-account`. Production's `.soonlane.com` cookies also reach staging hosts, so the staging API receives production session tokens on every browser call. Staging never reads them (own `AUTH_SECRET`, own prefix, SSR forwards only its own prefix's cookies, and the API never logs the cookie header), so staging runs only trusted refs ([ADR 0013](docs/decisions/0013-three-hosts-on-railway.md)). Details: [docs/deploy-railway.md](docs/deploy-railway.md).

The desktop app signs in through the system browser ([ADR 0007](docs/decisions/0007-desktop-sign-in-through-the-system-browser.md), [ADR 0015](docs/decisions/0015-desktop-app-with-its-own-ui.md)). The `desktopSignIn` plugin in `packages/auth` lets the signed-in browser trade the app's PKCE challenge for a one-time code (2 minutes, stored hashed in `verification`) at `/desktop/sign-in`. Without a `port` parameter the page returns the code through `soonlane://sign-in?code=…` and the window's `/desktop/callback` exchanges it and the app's verifier for a session cookie (`/desktop-sign-in/exchange`). The desktop app uses that path today. The server also has the return for the bundled UI, which the app does not call yet (SOON-148's desktop half): with `port`, the click sends the browser to `http://127.0.0.1:<port>/callback?code=…` (RFC 8252), and `/desktop-sign-in/token` trades the code and the verifier for a desktop token: the session token signed with `AUTH_SECRET` like the cookie, returned in the body with `no-store`. The app will send it as `Authorization: Bearer`; Better Auth's `bearer` plugin, with `requireSignature` and without its after hook (which would expose the web session's cookie value in a `set-auth-token` header), turns it into the session cookie for that request, so `getSession` is unchanged. Better Auth's `/sign-out` with the bearer token revokes the desktop session. Either way the app gets a session of its own, so signing out in the app leaves the browser signed in. The desktop session keeps the browser session's `createdAt`, so it is never fresh enough for account deletion when the browser session is not; `/desktop/sign-in?fresh=true` goes through Google first.

## Todoist import

With `TODOIST_CLIENT_ID` and `TODOIST_CLIENT_SECRET` set, a signed-in user can link Todoist read-only, see what an import would bring in and import it ([ADR 0016](docs/decisions/0016-todoist-link-through-better-auth.md)). "Continue to Todoist" on `/app/todoist` calls `todoist.cancel` (any earlier connection goes first) and then Better Auth's `/link-social`, which sends the browser to Todoist's consent screen; Todoist returns to `<API_URL>/api/auth/callback/todoist`, which writes the `todoist` row of `account` with the tokens encrypted and redirects to `/app/todoist` (with `?error=` when nothing was linked). The page asks `todoist.status`, and with a connection `todoist.preview`, which decrypts the access token, runs one full sync (`/api/v1/sync`, `sync_token=*`; a 429 waits for `Retry-After`, at least a second, at most 3 times and 10 seconds; the whole read stops after 20 seconds), maps it with `planTodoistImport` against the owner's label and project names and returns counts: tasks, new and matched labels, new and matched projects, and each change (`TODOIST_IMPORT_CHANGES`). Every open task counts, with or without a due date, except those already in the owner's `imported_todoist_task` records (`alreadyImported`); priority is inverted (Todoist 4 is Soonlane 1); a repeating task keeps its rule when its English due string is one rule a task name can type ("every day", "every 2 weeks", "every! 3 days", "every fri", "every 15th", "every jan 27"), optionally followed by "at" and a time, and the rule is stored as a new task's with its due date as the anchor; any other repeating task ("every mon, fri", "every 3rd friday", "starting", another language) arrives once on its current date and counts under `repeating`; projects and sections count when they hold an imported task, and the Inbox is not a project; a project matches an existing one by name ignoring case, and nested projects arrive flat. "Import into Soonlane" calls `todoist.import` with the browser's time zone; it reads Todoist again with the same guards, plans the same way and saves in one transaction: the records of the planned tasks first (`onConflictDoNothing` on owner and Todoist id, so a second submit or tab waits on the keys and saves nothing), then the missing projects and labels (`onConflictDoNothing` on their name indexes, a label taking its Todoist color when it is in `LABEL_COLORS`), then the tasks and their labels, 1,000 rows per insert. A date-only or floating due stays as written; a due pinned to UTC moves into the browser's time zone; a task without a due date arrives without one, so an Inbox task without a date lands in the Inbox. The records outlive their tasks, so a deleted or completed task does not come back. The import closes the connection on success and on failure, and sends `todoist_imported` after the commit. A failed preview, a cancel, a new link and a sweep every minute for rows older than 15 minutes revoke both tokens at Todoist and delete the row; a row whose revocation fails stays for the next sweep, and goes after an hour regardless, and meanwhile `todoist.cancel` fails so no new link starts. Tokens from a callback that stored no row are revoked by the callback's after hook. Todoist failures are logged by HTTP status or error name only, never with the token, URL or response body. The desktop app opens `/app/todoist` in the system browser.

## Database

Railway Postgres 18 through `pg` and Drizzle ([docs/railway-postgres.md](docs/railway-postgres.md)); locally Postgres 18 from `compose.yaml`. `Db` owns one pool per runtime (10 connections for the one long-lived process, 10 s `query_timeout`, an `error` listener) and closes it when the runtime is disposed; `Db.run` is the only place that creates `DbError`. Logs carry error names only, because driver errors embed SQL parameters such as session tokens. The API's `Bun.serve` answers any uncaught error with an empty 500 and logs only its name, for the same reason. The API's Railway pre-deploy runs the migrator before each deployment goes live; the web build never migrates ([docs/deploy-railway.md](docs/deploy-railway.md#migrations)).

## Server boundary

The web app depends on none of `@soonlane/db`, `@soonlane/auth/server`, `pg`, `drizzle-orm`, `posthog-node` or Effect; those live in `apps/api`. Its server-only code (`platform/`, `infrastructure/`, server-suffixed files, `*.handler.ts` and `routes/api.*`) never reaches the client bundle: TanStack Start import protection in `apps/web/vite.config.ts` fails the build on a leak and excludes the three browser-safe oRPC client files in `platform/rpc`. Server route handlers (`/api/auth/$`, `/api/rpc/$`, `/ingest/$`) run only from `server.handlers`, which TanStack Start keeps out of the client bundle.

## Analytics

PostHog (EU) receives product events, session replays and exceptions; the tracking plan is [docs/analytics.md](docs/analytics.md). In the browser everything hangs on `VITE_POSTHOG_KEY`: without it posthog-js is never downloaded, no consent banner appears and `/ingest` answers 404. On the API, `POSTHOG_KEY` turns on server events; without it `Analytics` is a no-op. With a key, each visitor's answer in the `<prefix>.consent` cookie (`soonlane.consent`, shared by every host under `soonlane.com`; staging's `soonlane-staging.consent` under `staging.soonlane.com`) decides: nothing before an answer, full analytics and masked replay when granted, cookieless anonymous events when denied or under Global Privacy Control; posthog-js never runs on `/desktop/*`. The browser side (consent banner, posthog-js client, browser event types) lives in `packages/analytics`; the API reads the answer through its root export. The browser sends through the first-party `/ingest` proxy (a server route that forwards to fixed PostHog hosts without the app's cookies). Server events (`user_signed_up` and `user_signed_in` from Better Auth's `events`, `first_task_created` from `TasksService`) and unexpected oRPC failures are queued, so no response waits for PostHog: posthog-node sends them in batches of 20 or every 5 seconds and flushes the rest when the runtime is disposed on shutdown. Events are queued only when the request carries a granted consent (the `AnalyticsConsent` reference, set per RPC request and per Better Auth hook); a failed batch is logged by name and never fails a request.

## Dates

A day is a `CalendarDate` (`YYYY-MM-DD`). The server cannot know the user's time zone, so `useToday()` reads the date in the browser (`useSyncExternalStore`, `undefined` during SSR, refreshed at local midnight and on tab focus). Calendar helpers work on UTC midnights, so they never cross a DST shift. The Upcoming list renders Overdue and every day from today to the end of the eighth week after the current one, then appends four more weeks whenever its end comes within a screen of the viewport, without end. Each loaded range has its own `tasks.list` query, so a range that is loading shows skeletons and a failed one shows Try again in place without hiding the tasks of the others; undated and overdue come from the first range. `useActiveDay` (a scroll tracker behind `useSyncExternalStore`, with ref callbacks on the sticky header and each day section) names the active day: the section at the top of the list, just under the header. The week strip and month label follow the active day's week; the arrows step one day (past the last rendered day the next weeks are appended first), the middle button names the active day (Today, Tomorrow, then e.g. Mon 9 Nov) and returns to today's section, and strip days scroll to their section, all landing just below the header (smooth unless the user prefers reduced motion). There is no `?week=` URL state.

## Shell

From `md` an icon rail is docked and the content keeps a rail-wide gutter; the content column is centered in the rest, so opening or collapsing the sidebar never moves it. From `xl` the owner's choice (full sidebar or rail) is docked and kept in the `soonlane-sidebar` cookie, read during SSR. Below `xl` the full sidebar opens over the content; phones use a drawer.

Inside the desktop app, `<html data-shell="desktop">` (set by its preload) turns on the `desktop:` variant: the rail, the sidebar and the phone bar leave 32px for the traffic lights and carry an `app-drag` strip that moves the window.

## Desktop app

`apps/desktop/src` mirrors the web app's layering ([ADR 0005](docs/decisions/0005-desktop-app-layout.md)). `main.ts` builds `AppLive` from `platform/` (`DesktopConfig` with the `APP_URL` baked in at build time, the `ManagedRuntime`, the Electrobun event helper). Modules: `window` opens the main window and saves its frame to `window-state.json`, ignoring a saved frame that no longer overlaps a display; `navigation` keeps the window on the app's exact origin and sends other web and mail links, and `/app/todoist`, to the system browser; `menu` sets the app menu; `sign-in` opens the desktop sign-in in the system browser with the challenge of its pending verifier (a new one when none is pending) and, on a `soonlane://` link, loads `/desktop/callback` with the code and that verifier. macOS delivers `soonlane://` links only to a copy of the app in `/Applications`.

`quick-add` registers ⌥Space with Electrobun's `GlobalShortcut` and asks macOS for Accessibility access, which the shortcut needs to work in other apps. A press opens `/app/quick-add` in a small always-on-top window without a title bar on the display under the cursor, or brings the open one forward; it shares the main window's preload, navigation rules and link handling (`openAppWindow`, `followNavigation`). `dock-badge` sets the Dock icon's badge through `bun:ffi` and the Objective-C runtime (`platform/macos`), since Electrobun has no badge API. The page talks to the main process only through the preload's `__electrobunSendToHost`, with two messages decoded by Effect Schema: `quick-add-done` closes the Quick Add window, and `dock-badge` carries the count of open tasks overdue or due today. The web app computes that count from the Today list in the TanStack Query cache (`syncDockBadge`), and sends 0 when sign-out clears the cache ([ADR 0010](docs/decisions/0010-desktop-quick-add-and-dock-badge.md)).
