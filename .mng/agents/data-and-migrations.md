Find changes that lose or corrupt stored data, break a deploy's migration, or leave the schema and the code out of step.

Check, for every change under `packages/db`:

- A file inside an existing `packages/db/migrations/<timestamp>_*/` directory changed. Deployed migrations are immutable; the only valid change is a new directory generated by `bun run db:generate`.
- The new `migration.sql` matches the schema change in `packages/db/schema` and does what the schema says, and no more.
- The migration drops, renames or retypes a column or table that holds data, adds `NOT NULL` without a default to a table with rows, or changes a cascade (`onDelete`) so that deleting a user, task, label or project now removes or keeps rows it did not before. A rename that Drizzle generated as drop plus add loses the column's data.
- A unique index, check or foreign key was renamed or removed while the service still maps it by name (`isUniqueViolation`, `isForeignKeyViolation`, `isCheckViolation` with a constraint name): the error then reaches the user as a 500 instead of CONFLICT or NOT_FOUND.
- Better Auth's tables (`user`, `session`, `account`, `verification`) change without the matching change in `packages/auth`.
- A backfill is a migration instead of a script in `packages/db/scripts/`, or the script writes without a dry run first.

For repository and service code, check updates and deletes: a `where` that matches more rows than intended, a delete that leaves orphans the schema does not cascade, a transaction body (`Db.transaction`, rerun on deadlock) that does anything besides database writes, and subtask writes that skip `lockPath`/`lockPaths`.

Proof names the migration or query line, the rows it touches and what is lost or wrong afterwards. A data-loss claim needs the column or rows that hold data today.
