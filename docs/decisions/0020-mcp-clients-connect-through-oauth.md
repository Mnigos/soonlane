# ADR 0020: MCP clients connect through OAuth with Better Auth's MCP plugin

**Status:** Proposed
**Date:** 2026-11-24

## Context

[SOON-29](https://linear.app/rigtch/issue/SOON-29) lets AI agents (Claude Code, Codex CLI, claude.ai connectors, ChatGPT connectors, Executor) read and change a user's tasks through an MCP server. [SOON-236](https://linear.app/rigtch/issue/SOON-236) is its second step: the authorization server, the Allow page and the list of connected agents. [SOON-241](https://linear.app/rigtch/issue/SOON-241) adds the MCP endpoint with tools that read tasks; write tools follow.

The owner settled that agents sign in through OAuth from the first version with Better Auth's official MCP plugin, with no personal tokens, that read and write are separate scopes the user picks from, and that nothing deletes. The MCP authorization spec of 2026-07-28 says authorization servers SHOULD support Client ID Metadata Documents (CIMD) and keeps Dynamic Client Registration only for backwards compatibility. What Better Auth 1.7.27 does was read from `@better-auth/mcp`, `@better-auth/oauth-provider` and `@better-auth/cimd`, not from memory.

## Decision

- **The provider.** `mcpAuthorization()` in `packages/auth/src/mcp-authorization.handler.ts` adds Better Auth's `jwt`, `mcp` and `cimd` plugins to `createAuth`. Clients, consents, tokens and signing keys live in eight tables (`packages/db/schema/oauth.schema.ts`); every reference declares `onDelete`, so deleting a user removes their connections and tokens.
- **Issuer and resource.** The issuer is the API's origin, set as the `jwt` plugin's issuer, so an agent that reads only the root's metadata finds it; the endpoints stay under `/api/auth`. Tokens are JWTs for the resource `<API origin>/mcp`, the URL a user types into claude.ai. The API routes `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource[/mcp]` to Better Auth, which answers them in its plugins' `onRequest` before its base path check.
- **Scopes.** `tasks:read` (tasks, projects and labels), `tasks:write` (creating and changing them) and `offline_access`, all listed in the authorization server metadata. Edit implies see: `tasks:write` implies `tasks:read`, as the 2026-07-28 spec requires servers to account for scope hierarchies, so the Allow page ticks see with edit and posts `tasks:read` with `tasks:write` when the agent requested both. For a write-only request the provider refuses a scope outside the signed request, so the page posts `tasks:write` alone under a single checkbox that names the reading too ("See your tasks, projects and labels, and add, edit and complete tasks"). A consent holding `tasks:write` alone is listed as "Can see and edit tasks" and will be accepted wherever `tasks:read` is required. No OpenID scope, so no ID token, userinfo or OpenID configuration. Only the authorization code and refresh grants.
- **Registration.** Clients identify themselves with a CIMD document, fetched by `@better-auth/cimd/node`'s transport, which resolves the host once, refuses non-public addresses and pins the connection. Open dynamic registration is one `createAuth` option, `dynamicMcpRegistration`, off; when on it comes with a guard that refuses fetched or posted addresses and long or unprintable names. While off, `/oauth2/register` answers 403 as the plugin does. A hosted agent without CIMD gets a client the operator registers.
- **Verified agents.** An HTTPS client id is a CIMD URL that Better Auth fetched from that host, so its host is shown as verified (`readVerifiedMcpClientHost`); any other client is an "Unverified app".
- **Allow page.** `/mcp/allow` on the web app, under the session layout, names the agent, its verified host or the unverified line, the host the answer goes to (or "an app on this computer" with a warning for a loopback address or any scheme but HTTP(S), which no document can prove belongs to the agent), and a checkbox per requested task scope. The ticked boxes are the `access` search param; without it everything requested is ticked, and the server refuses any scope outside the original request. An expired request shows the expired message instead, found by the server's clock on the first load or from the provider's `invalid_signature` answer, never by the device's clock, which can run fast. The answer carries the id of the account the page showed, and a before hook on `/oauth2/consent` refuses it with `MCP_ACCOUNT_CHANGED` before anything is stored when the session holds another account, so a page left open while another tab signed in elsewhere cannot grant that account's tasks; the page then offers a reload. Every response under `/mcp/`, an error page included, refuses framing and sends no referrer (`handOffPathMiddleware`), which also answers another letter case with 404 so Nitro's `no-store` rule always applies.
- **The signed request.** The provider sends the browser to `/login` and `/mcp/allow` with the request signed (`sig` over every param except itself, `ba_param` naming the signed ones). TanStack Router parses every search value it can into a number, a boolean or JSON (`state=1e5` becomes `100000`), rewrites the URL whenever the validated search differs and on every navigation, and turns the repeated `ba_param` into a JSON array; any of these breaks the signature. `/login` validates with a loose schema blind to the signed params, so the router never rewrites its URL and the browser client reads the request as signed. The Allow page's first load redirects to itself with the provider's whole query, read from the request URL on the server or `window.location` in the browser, as one `request` param that starts with `?`, which the router neither parses nor rewrites; the page reads the agent, redirect, scopes and expiry from it with `URLSearchParams` and posts its signed params as `oauth_query` unchanged. Both pages are reached only by a document load (the provider's redirect, Google's callback, and Better Auth's browser client setting `window.location.href`), which is what keeps the raw signed query intact, so no code may navigate to them with a signed query through the router; a signed-out visitor on the Allow page is sent to `/login` with the same query by a document load too. A query whose signature is forged or altered still renders the page and is refused when the user presses Allow or Cancel, because only the API can verify the signature.
- **Disconnect.** `mcp.disconnect` deletes the consent row with the user's refresh and access tokens for that client in one transaction. Better Auth's own `/oauth2/delete-consent` would leave the refresh token working, because the refresh grant never reads consent. An hourly sweep in `McpService` removes connections unused for 30 days, the refresh token's lifetime, so a kept consent cannot let a later sign-in skip the Allow page. A rotated refresh token presented again within 30 seconds returns the same new pair, and after that its reuse is refused and revokes the agent's whole token family; that window is the MCP plugin's `refreshTokenReuseInterval` default, kept so an agent that sends two refreshes in parallel does not log itself out.
- **A new Allow starts clean.** The provider's code exchange and refresh grant never read the connection, so a code issued before a Disconnect, or a refresh token that outlived it, would mint tokens dated after a new connection, which the per-request check accepts, and each refresh would write another. So when the user allows an agent they have no connection to, `consentAccountGuard` (a before hook on `/oauth2/consent`, after its account check) first deletes that user's refresh tokens, stored access tokens and unexchanged authorization codes for that client (`clearEarlierMcpGrants`); then the provider stores the connection and issues the new code. Codes live in `verification` as `{"type":"authorization_code",...}` JSON holding `userId` and `query.client_id`; the guard narrows the rows with Better Auth's adapter and matches the parsed value exactly. Allowing again on a live connection (other scopes) and Cancel delete nothing. A token guard on `/oauth2/token` was not added: it would race the same way, at a lookup per refresh.
- **Closed endpoints.** Session-backed client and consent management, introspection, OpenID logout and its confirmation, userinfo, the public-client prelogin and the `jwt` plugin's `/token` are in `disabledPaths`, the plugin's `set-auth-jwt` header is off, and `clientPrivileges` refuses every client change from a session, so no signed-in user can register a client that phishes others. The authorization server metadata still lists `introspection_endpoint` and `backchannel_logout_supported: true`, because the provider writes both unconditionally while its `jwt` plugin is on and offers no option to drop them; MCP clients use neither, and the introspection path answers 404.
- **The MCP endpoint.** `/mcp` serves MCP over streamable HTTP through `@modelcontextprotocol/server` 2.4.0's `createMcpHandler`, stateless, with a new `McpServer` per request. `legacy: 'stateless'` serves 2025 clients too (their GET and DELETE answer 405), and `maxSubscriptions: 0` refuses `subscriptions/listen`, since a tool list fixed per request has no change to announce and an open stream would outlive the request's checks. The server declares `capabilities: { tools: { listChanged: false } }`, so a 2026-07-28 client is not invited to listen, and a connection without a task scope gets an empty `tools/list`. A request with an `Origin` header comes from a browser and gets 403; no browser host is served, so there is no CORS.
- **The challenge.** A request without a valid token gets the plugin's 401 with `resource_metadata` and `scope="tasks:read tasks:write"`. `offline_access` stays out, as the 2026-07-28 spec keeps authorization-server-only scopes out of resource challenges; clients add it to their authorization request because the authorization server metadata lists it, and get a refresh token.
- **The per-request check.** The `Auth` port's `serveMcpRequest` verifies the token with the plugin's `requireMcpAuth`, issuer and resource passed explicitly. `McpService.admit` then requires the `oauth_consent` row of the token's `azp` and `sub` with `created_at <= iat`: one indexed read on `(user_id, client_id)` per request. A token is bound to the connection it was issued under, not only to the user and client, so a token from before a Disconnect and a new Allow is refused. Both values are whole seconds: the provider writes `iat` as `floor(now / 1000)` and the consent's `created_at` from the same floored clock when it creates the row, and a later Allow of the same connection changes only its scopes and `updated_at`. A token issued in the second the connection was allowed passes. A token whose connection is missing or newer gets the same 401 as an invalid token. The owner is `sub` parsed with `userIdSchema`.
- **Scopes on a request.** The tools a request sees come from the scopes both the token and the connection grant, each with edit implying see, so allowing an agent again with fewer boxes narrows its earlier tokens at once. `tasks:read` registers the read tools; tools are never registered without their scope.
- **The tools.** Seven read tools: open tasks for a view (`today` from the client, a date range, a label, a project), search, one task, a task's subtasks, completed tasks in a range, projects and labels. Each calls the existing services with the request's owner and never queries a table. Inputs are the contract's fields with descriptions (`mcp-tool.schemas.ts`); the JSON Schema drops refinements and `z.date()` has no JSON Schema form, so completed-task ranges travel as ISO date-times with offset and every tool parses its arguments again with the procedure's own input schema. Results are JSON in one text block, without an output schema, since `taskSchema`'s dates have no JSON Schema form either. The lists that are unbounded today (open, completed and sub-tasks, projects, labels) stop at 100 items per list with `hasMore`; search keeps its 50. The services still load the whole list; loading only 100 rows is a follow-up if lists grow.
- **Last used.** `oauth_consent.last_used_at`, Soonlane's own column, is written from `/mcp` requests when the recorded value is older than a minute, so most requests only read. The list of connected agents shows it, and the 30-day sweep counts from the latest of it, `updated_at` and `created_at`.
- **The rate limit.** All of a user's agents share 120 requests a minute, counted in `rate_limit` under `mcp:<user id>` with one atomic upsert per request, as the email code limiter counts; over it the endpoint answers 429 with a JSON-RPC error and `Retry-After: 60`.
- **The log.** One physical line per request, `status=… tool=… outcome=… error=… durationMs=…`, as the API's other lines pass scalar fields. A `tools/call` the SDK refuses before a tool runs is named from a copy of the body, read only then: the tool when it is one this request registered (`INVALID_ARGUMENTS`), never another name (`UNKNOWN_TOOL`). No token, header, body, arguments, URL query, SDK message or task text, and no analytics.
- **The CIMD fetch on Bun.** The transport uses `node:https` with a custom `lookup`. On Bun 1.4.2 (2026-11-23, macOS) a probe showed Bun calls `lookup` with `all: true` and connects only to the returned address, checks the certificate against the hostname, falls back from a refused IPv6 address to IPv4, returns redirects unfollowed and refuses loopback, private and metadata addresses. The plugin adds a 5 s timeout and a 5 KiB cap. Rerun the probe on every Bun upgrade.

## Consequences

- Signing out of the web app does not disconnect agents: `offline_access` refresh tokens outlive the browser session. Deleting the account removes every connection by cascade.
- A connection is per user and client, so disconnecting Claude Code ends it on every machine.
- Allowing the same agent from two tabs at the same moment can answer one of them with an empty 500: the provider looks the consent up before creating it, and the unique index on `oauth_consent (client_id, user_id)` refuses the second row. The index stays, because a duplicate row would survive a Disconnect and let the agent skip the Allow page; one tab sends its answer once.
- "Last used" is precise to the minute and counts only MCP requests; a connection that only refreshes its tokens is removed 30 days after its last request or Allow.
- After Disconnect the agent's tokens stop working at its next request, because `/mcp` requires the connection, and its refresh token is deleted with it. What is in flight can still give tokens: a refresh whose rotated token the provider writes just after the Disconnect's delete, and an authorization code issued before the Disconnect and exchanged within its 600 seconds (the provider's `codeExpiresIn` default). Such tokens have no connection, so `/mcp` refuses them and the hourly sweep deletes them; if the user allows the agent again first, that Allow deletes them and any unexchanged code before the new connection exists, so nothing issued before it obtains or keeps a working token.
- One window remains: a refresh or code exchange that reads its old credential before a new Allow's delete and writes its result after it, while the provider stores the new connection, keeps working under that connection. It needs the old credential's holder to refresh during the milliseconds of that Allow request; refreshes come about once an hour.
- A token issued in the same whole second in which the user disconnects and completes a new Allow passes the check: `iat` and the connection's `created_at` are whole seconds, and `<=` must stay because an agent normally exchanges its code in the consent's second. With the deletion above, no leftover credential mints such a token after the new Allow, so what remains is an access JWT issued within that one second before the Disconnect and the completed Allow; it expires within the hour. Accepted: the JWT carries no reference to the connection (`sid` is the browser session, `jti` is random), so no exact discriminator exists without a claim or a lookup per request.
- Rotating `AUTH_SECRET` makes the signing keys and stored replay responses unreadable, so every agent must connect again.
- Rejected: personal tokens (settled by the owner), opaque tokens with introspection (a database read and a network hop per call for what a JWT carries), a short access token lifetime alone as Disconnect (it still lets the agent refresh), Better Auth's `/oauth2/delete-consent` as Disconnect, an issuer at `/api/auth` (agents that read only the root's metadata would not find it), open dynamic registration by default, an output schema per tool (a hand-written copy of `taskSchema` with string dates), a database write for "last used" on every request, a session per MCP client (state the 2026-07-28 protocol no longer needs), and a connection generation carried in tokens (the deletion at Allow ends the same chains without a claim the provider cannot carry through rotation).
