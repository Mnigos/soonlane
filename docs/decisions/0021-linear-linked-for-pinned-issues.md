# ADR 0021: Linear linked through Better Auth and kept, to pin issues to tasks

**Status:** Proposed
**Date:** 2026-11-24

## Context

[SOON-28](https://linear.app/rigtch/issue/SOON-28) lets a user pin Linear issues to a task and see each one's current title and status. The owner ruled out a mirror: issues never become tasks, and Soonlane never writes to Linear. Showing a live status means Soonlane reads Linear on the user's behalf whenever an edit card opens, for as long as the user keeps Linear connected. [SOON-239](https://linear.app/rigtch/issue/SOON-239) connects the account from the user menu; pinning comes after it.

[ADR 0016](0016-todoist-link-through-better-auth.md) links Todoist through Better Auth's `genericOAuth` for at most 15 minutes, because the import reads Todoist once. That shape does not fit here: a pin is read again days and weeks later.

Facts checked on 2026-11-24 against the locked Better Auth 1.7.27 (`node_modules`, not memory):

- Better Auth ships a `linear` social provider (`@better-auth/core/dist/social-providers/linear.mjs`): default scope `read`, a refresh against `https://api.linear.app/oauth/token`, user info from the GraphQL `viewer`. It takes `getUserInfo`, `disableSignUp` and `disableImplicitSignUp` like any social provider and runs through the same `/link-social` and `/callback/:id` endpoints as `genericOAuth`, so ADR 0016's guards apply to it unchanged; `genericOAuth` is not needed. It sends no PKCE challenge; the client secret authenticates the code exchange.
- Better Auth's `refreshToken` endpoint refreshes through the provider and writes the new pair back encrypted. `disabledPaths` blocks it only over HTTP; a server call (`auth.api.refreshToken` with the account and user id) still runs. It reports every failure as `FAILED_TO_REFRESH_ACCESS_TOKEN`, without Linear's reason.
- Linear issues a 24-hour access token and a refresh token valid for 30 days from issue, rotated on each refresh; every Linear OAuth app moved to refresh tokens on 2026-04-01. Revocation is `POST https://api.linear.app/oauth/revoke` with the token alone in the form (`token`, optional `token_type_hint`); it answers 200 when it revoked the token, 400 when it could not (such as a token revoked before), 401 `Token not found` for a token it does not know, and other 401s for a request it cannot read (an empty body, or `Conflicting access tokens` when a Bearer header comes next to `token`). Client credentials, in a Basic header or the form, are ignored (probed with dummy tokens: 401 `Token not found` either way). A failed refresh may be retried with the same refresh token for 30 minutes. GraphQL answers a bad token with 401.
- Bun's `fetch` (bun-types 1.4.4) has no whole-request deadline by default, only a socket idle timeout of 5 minutes (`BUN_CONFIG_HTTP_IDLE_TIMEOUT`) that every byte resets, and Better Auth's built-in refresh passes no signal, so a silent Linear token endpoint could hold a refresh that long. The `linear` provider therefore gets its own `refreshAccessToken`: Better Auth's request builder (`refreshAccessTokenRequest`, `client_secret_post`) and token mapping (`getOAuth2Tokens`) with a 10-second `AbortSignal.timeout`.

## Decision

- Linear is Better Auth's built-in `linear` provider, scope `read` only, configured in `createAuth` only when `LINEAR_CLIENT_ID` and `LINEAR_CLIENT_SECRET` are both set.
- It is a link, never a sign-in, with the guards ADR 0016 gives Todoist, now shared by both providers in `provider-link.handler.ts`, which names no provider; `createAuth` passes the configured ones: `/sign-in/social` refuses `linear`, user info is `null` outside a signed-in user's link state, `/link-social` accepts only a link-only provider, with no scopes or parameters beyond the return addresses, from the browser, and only while the user has no row of that provider, and tokens from a callback that ends without a row are revoked at once, best effort. A callback neither updates a link-only row nor creates a second one for the same owner, so of two links racing, from one session or two, the later one's tokens are revoked; the API's refreshes still update the `linear` row. `linear` is a trusted provider whose user info carries the linking user's own email. One Linear account per Soonlane user.
- Unlike Todoist, the `linear` row stays until the user disconnects or deletes the account. Its tokens are encrypted with `encryptOAuthTokens`, never sent to the browser (the token endpoints stay disabled over HTTP), and read only by the API through Better Auth's cipher.
- The API (`modules/linear`) refreshes an access token within 5 minutes of expiry through `auth.api.refreshToken`, which writes the rotated pair back. One permit per API process (a one-permit semaphore; the API is one process) covers refreshing and Disconnect, since Linear rotates the refresh token: a second concurrent refresh would send a spent one and lose the connection, and a Disconnect during a refresh could revoke the old pair while the new one is written. A fresh access token is read without the permit. A refresh runs in its own fiber that holds the permit until Better Auth's request settles, which the provider's 10-second deadline bounds, reading the row again first; the status call waits for it at most 15 seconds and otherwise reads lapsed, while the refresh goes on and the next refresh or Disconnect reads the pair it wrote. A failed refresh logs Better Auth's code only.
- The connection reads as lapsed when a refresh fails or times out, the stored token cannot be decrypted, or Linear's GraphQL refuses the token (401 or `AUTHENTICATION_ERROR`, as after the user removes Soonlane in Linear). Better Auth hides Linear's reason for a failed refresh, so a Linear outage during a refresh also reads as lapsed until the next status read tries again; other GraphQL failures are an outage, which hides the menu item. Reconnect, like Connect, opens the web page `/linear`, a browser-only route loader that leaves a healthy connection alone, disconnects a lapsed one and runs the link again, so the guard's one-row rule holds.
- `linear.status` answers not configured, not connected, connected with the workspace's name (one GraphQL read, made when the user menu opens) or lapsed.
- Disconnect, in the user menu, revokes both tokens at Linear and deletes the row only when each came back revoked (200), unknown to Linear (401) or revoked before (a 400 whose body says so), which closes a lapsed connection whenever Linear answers in those words. Any other answer keeps the row, logs the status with Linear's short `error` string, and returns an error, so the user can retry. Account deletion revokes both tokens best effort in an account delete hook of the `linear-link` plugin, which runs after deletion's checks pass and before the rows go.
- The desktop app opens `/linear` in the system browser, where the OAuth state cookie and the session live ([ADR 0007](0007-desktop-sign-in-through-the-system-browser.md)).
- Pins (SOON-28) keep the issue's ID, identifier, title and URL from the moment of pinning, so they still read and open without a connection. Status is never stored; it is fetched live for one task's pins in one GraphQL request.

## Consequences

- An encrypted Linear refresh token sits in the database for as long as the user stays connected. A dump without `AUTH_SECRET` does not reveal it; rotating `AUTH_SECRET` makes it unreadable, the connection reads as lapsed, and Disconnect deletes the row without revoking, since nobody can revoke a token that cannot be read.
- Opening the user menu with Linear connected costs one Linear request; opening an edit card with pins costs one more. A Linear outage hides the Linear item while it lasts.
- A user who leaves Soonlane for 30 days reconnects once.
- `read` covers every team the user can see in Linear; Soonlane cannot narrow it to one team.
- A second API replica would need a lock shared through the database instead of the process. A status read due for a refresh waits behind a refresh or Disconnect in progress, at most 15 seconds; a status read with a fresh token racing a Disconnect reads lapsed until the next read. 
- Linear's wording is matched loosely (`Token not found` for a 401, `revoked` for a 400); a different wording keeps the row and Disconnect fails until it changes (to be confirmed on the first manual run with a real grant).
- Refreshes share one process permit: a refresh waiting on a slow Linear token endpoint (at most its 10-second deadline, plus the database write) makes other due refreshes and Disconnect wait, and those users read lapsed meanwhile.
- A refresh still running when the API shuts down (it is detached, so disposing the runtime neither waits for nor interrupts it) can lose the rotated pair; Linear accepts the previous refresh token again for 30 minutes after a lost response, and otherwise the user reconnects.
- Two link callbacks within milliseconds can both pass the create check and store two rows. Nothing leaks: Disconnect revokes and deletes every row of the owner, account deletion removes them, and `/link-social` refuses another link meanwhile. A partial unique index on `(user_id, provider_id)` for link-only providers closes it once SOON-236 has merged.
- Account deletion's revoke runs inside Better Auth and takes no part in the API's permit; a refresh during `/delete-user` could write a pair the hook never revokes, and the row goes with the user anyway.
- Rejected: a 15-minute link as in ADR 0016 (status would need a reconnect on every visit); `genericOAuth` with Linear's endpoints (the core provider takes the same guards); refreshing with a hand-written token request to tell a refused refresh from an outage (repeats Better Auth's refresh and its encrypted write); pasted links without OAuth (no title or status; the owner chose OAuth); a mirror of assigned issues as tasks (ruled out by the owner); webhooks from Linear (needs a public endpoint and per-workspace setup for a status that is read only when a task is opened).
