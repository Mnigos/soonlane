# ADR 0009: Open sign-in for any Google account

**Status:** Proposed
**Date:** 2026-11-06

## Context

Until now Soonlane let in one Google account, `OWNER_EMAIL` ([ADR 0003](0003-better-auth-in-a-package-behind-an-effect-layer.md)): the user-create hook rejected everyone else, and `requireOwner` and `identity.me` checked the address again on every request. On 2026-11-06 Soonlane became a public product, so anyone can sign up and gets a private task list. Data was already per user: `task.owner_id` references `user.id` with `onDelete: cascade`, and every `TaskRepository` query filters by `ownerId`.

What Better Auth 1.7.18 offers (read from `node_modules/better-auth`, not from memory):

- `user.deleteUser` deletes at once when no verification email is configured. Without a password it requires a fresh session: a session older than `session.freshAge` (default one day) gets `SESSION_EXPIRED`.
- `rateLimit` with `storage: 'database'` keeps one row per client IP and path in a `rateLimit` model (`key`, `count`, `lastRequest` in ms) and updates it atomically. It is on only in production by default, and the memory store is per process.
- The limiter reads the client IP from `advanced.ipAddress.ipAddressHeaders` (default `x-forwarded-for`) and trusts a header only when it holds a single address. [Vercel overwrites `x-forwarded-for`](https://vercel.com/docs/headers/request-headers#x-forwarded-for) with the client's address and does not forward one a client sends.

## Decision

- Any Google account whose address Google reports as verified can create an account. `ALLOWED_EMAILS` (comma-separated, trimmed, lowercase) is optional: when set, only those addresses can create an account, and existing accounts keep signing in. Production, previews and development run without it; it exists for self-hosted copies and to close sign-ups quickly. A rejected sign-up returns to `/login?error=SIGN_UPS_CLOSED`.
- `requireUser` replaces `requireOwner`: `UNAUTHORIZED` without a session, otherwise `context.user`. "Owner" now means the owner of a task; the `owner_id` column and the `ownerId` parameters stay. The `FORBIDDEN` contract error is gone.
- "Delete account" in the user menu calls `/delete-user` after a confirmation dialog. It keeps Better Auth's default `freshAge`, so a session older than a day must sign in with Google again first. Google ID-token sign-in is off (`disableIdTokenSignIn`), so a fresh session always comes from a Google redirect. A desktop hand-off never makes a session fresher than its source: the desktop session keeps the browser session's `createdAt`. To re-authenticate in the desktop app, the dialog opens `/desktop/sign-in?fresh=true`, which goes through Google even when the browser is signed in. The re-authentication passes the current address as Google's `login_hint` and asks Google for a new login with `prompt=login` and `max_age=0`. Google does not document `prompt=login` and may skip the password after its own risk check, so since SOON-51 the server also checks the ID token's `auth_time` (see the SOON-51 update). The dialog's re-authentication sends the current `/app` URL with `deleteAccount=true`, absolute on the current origin, as both the callback and the error callback. The return from Google, also after a cancel or a failed sign-in, reopens the dialog; a preview's cancel stays on the preview, and closing the dialog removes the parameter. The cascades remove sessions, accounts and tasks with the user.
- Better Auth rate limits `/api/auth` in Postgres (`rate_limit` table), also outside production: 100 requests a minute per IP, 10 a minute for `/sign-in/social`, `/desktop-sign-in/code` and `/desktop-sign-in/exchange`, 5 an hour for `/delete-user`. It keys on `x-forwarded-for` only.
- An after hook sets `soonlane-signed-in=1` (not HttpOnly, the session cookie's `Secure` and `SameSite=Lax`, the session lifetime) whenever a request creates or refreshes a session, including the desktop code exchange, and clears it after sign-out and a successful deletion. It carries no user data; static pages read it to show "Open app" instead of "Log in".

## Consequences

- ADR 0003's owner-only hook and owner policy are superseded; the rest of ADR 0003 stands. Its text stays as written.
- A stale or missing hint only changes which header link a static page shows; the session cookie still decides access.
- On Vercel a request whose `x-forwarded-for` is missing or holds a chain falls into one shared bucket per path. Behind another proxy in front of Vercel, the limiter would need `x-vercel-forwarded-for` or `trustedProxies`.
- Every request to `/api/auth` now writes to `rate_limit`; Better Auth prunes rows older than the longest window (one hour) when a window resets.
- Rejected: memory storage for the limiter (each Vercel function instance would count alone), `x-real-ip` and `x-vercel-forwarded-for` (Vercel's docs promise the overwrite only for `x-forwarded-for`), a custom `freshAge` (the one-day default already asks for a recent Google sign-in), keeping the owner gate behind a flag (two code paths for one product).

## Update 2026-11-12 (SOON-119)

Better Auth runs on the API and reads the client IP only from `x-soonlane-client-ip`, which the API's HTTP entry sets and a client cannot: from the web server's `x-soonlane-visitor-ip` (taken from Vercel's `x-forwarded-for`) when `x-soonlane-proxy-secret` matches `API_PROXY_SECRET`, a wrong secret is refused with 403; otherwise from Railway's `X-Real-IP`, or `CF-Connecting-IP` when that address is a Cloudflare edge. See `docs/deploy-railway.md`. The signed-in hint is now `<prefix>.signed_in` on the environment's shared domain (ADR 0013).

## Update 2026-11-16 (SOON-51)

`/delete-user` now checks when the user last logged in to Google, not only how old the session is. Better Auth's one-day `freshAge` check still runs after it.

- **Request.** On every Google `/sign-in/social`, a before hook adds `claims={"id_token":{"auth_time":{"essential":true}}}` to the authorization URL and replaces any `claims` a client sends. Builds of the apps that are already installed ask for it too. Google returns `auth_time` only while "Session age claims" is on for the OAuth client's project (Google Auth Platform, Settings, Advanced settings) and the app is published and verified.
- **Check.** A before hook on `/delete-user` reads `auth_time` from the ID token Better Auth stores on each of the user's Google account rows at every Google sign-in, and takes the newest as A. It decodes the payload without verifying the signature, because Better Auth stores only tokens it got from Google's token endpoint and Google ID-token sign-in is off. The deletion goes through only when A is at most 5 minutes old, at most 60 seconds in the future, and the session started no earlier than 60 seconds before A. The 60 seconds allow for the clocks of Google and the API disagreeing, and they are an accepted gap: a session created up to 60 seconds before the login passes, and so does an `auth_time` up to 60 seconds in the future. A session stolen more than 60 seconds before the owner's fresh login fails. A hand-off session keeps its browser session's `createdAt`, so the Android app passes when its browser just signed in and fails when it reused an older browser session.
- **Refusal.** A missing, malformed, old or future `auth_time` answers `SESSION_EXPIRED`, which the web dialog and the apps already turn into a fresh sign-in. Some of these refusals also carry a `reason` (see "Google skips the check"). Refusals count toward the limit of 5 `/delete-user` calls an hour per IP, so a user who keeps retrying without a fresh Google sign-in gets a 429 after the fifth call in an hour. The API logs the reason and the age, at `warn` for a missing or future `auth_time` and at `info` otherwise, and never logs the token. There is no fallback to `freshAge` alone: with Session age claims off, nobody can delete an account.
- **Desktop.** `/delete-user` refuses any request with an `Authorization` header (403), because a before hook cannot see a bearer session. The desktop app has no account actions ([ADR 0015](0015-desktop-app-with-its-own-ui.md)), so the re-authentication through `/desktop/sign-in?fresh=true` described above no longer exists for deletion. A desktop token sent as a cookie is a session like any other and meets the same check.
- **Google skips the check.** The staging test on 2026-11-17 confirmed the risk Google's documentation leaves open. In Chrome already signed in to Google, `prompt=login` and `max_age=0` showed only the account chooser, and `auth_time` kept the earlier login, so every retry was refused. When the login is older than 5 minutes and the session started more than 60 seconds after it, that session came from a Google sign-in that kept the old login. The refusal then stays `SESSION_EXPIRED` and adds `reason: GOOGLE_LOGIN_NOT_RENEWED` (SOON-220), so app builds and web bundles that predate it still offer their sign-in. This is often the first refusal a user sees, because most people signed in to Google long before Soonlane. The web dialog and the Android app tell the user to sign out of Google in the browser and then press "Continue with Google". Google is then expected to check the user, by password or passkey, which renews `auth_time`. This recovery is not verified yet: on web it counts as verified only once the staging steps in `docs/deploy-railway.md` show a deletion after signing out, and on Android only once Igor tests it on a phone, where Chrome ties Google sign-in to the device's accounts. The iPhone ignores the reason, because its sheet keeps no Google session.
