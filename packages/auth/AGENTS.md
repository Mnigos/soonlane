# packages/auth agent rules

- `@soonlane/auth/server` (`createAuth`) is server-only and imported only by `apps/api` (`createAuth` only in `modules/identity/infrastructure/better-auth.layer.ts`); `@soonlane/auth/client` is the browser client; the root exports the pure sign-up policy, the signed-in hint's name for a cookie prefix (`getSignedInHintCookie`) and the desktop sign-in contract (scheme, loopback address, paths, parameters, PKCE helpers, the bundled page's origin) and the Android hand-off's paths, package and the mobile app's header (`mobile-sign-in.constants.ts`), which `apps/desktop`, `apps/mobile` and the API import too.
- The desktop app's bearer token is the session token signed with the auth secret (`/desktop-sign-in/token`). Keep `bearer` at `requireSignature: true` and without its after hook, which would put the web session's cookie value in a header scripts can read. Before hooks never see a bearer session (Better Auth applies the header only after all of them run), so a hook that looks up the session refuses requests with `authorization`.
- No Effect here: configuration, the database and the logger arrive as arguments.
- Every log argument goes through `redactLogArgument`; Drizzle errors embed session tokens.
- Better Auth reads the client IP only from `CLIENT_IP_HEADER`, which the API's HTTP entry sets. Keep `AUTH_BASE_PATH`, the Google and Todoist redirect URIs (on the API host) and the API's `TRUSTED_ORIGINS` aligned.
- Google only signs in and Todoist (`todoistLink`, a generic OAuth provider) is only linked: `/sign-in/social` refuses Todoist, `/link-social` accepts nothing else, and Todoist's user info is `null` outside a link. Provider tokens are stored encrypted; the endpoints that return them to the browser are disabled, and the API decrypts them with `readStoredOAuthToken`.
- Cookie names come from the caller's `cookiePrefix`; never a fixed name. Return addresses are validated by the `returnAddresses` plugin (`onRequest`, before Better Auth's own checks) against `trustedOrigins` only, plus the mobile app's schemes on `/sign-in/social` (never on `/link-social`), never Better Auth's own list, which also trusts relative paths and the API's origin.
- The mobile app signs in through `@better-auth/expo` (`expoSignIn`), used without its `init`: that trusts `exp://` on `NODE_ENV`, which `bun build` inlines as `development` unless the build sets it. `exp:` is trusted only with `trustExpoGo` (the API passes `APP_ENV=development`). `/expo-authorization-proxy` signs the OAuth state into any browser that opens it, so the before hook lets it through only for one Google authorization URL whose state row is pending, has no `link`, and returns only to an app scheme (`callbackURL`, `newUserURL`, `errorURL`). A callback that redirects to an app scheme sets no browser cookie; the app gets them only in `?cookie=`.
- The Android app signs in through `desktopSignIn` too: `/android/sign-in` on the web mints the code for its challenge and returns it only through the App Link `/android/callback` on its own origin, and the app exchanges it at `/desktop-sign-in/exchange`. Keep the plugin's checks the same for both apps; `x-soonlane-app: mobile` on the exchange only labels the session `mobile` in `sessionCreated`. Never add a cookie-carrying or caller-chosen return to it.
